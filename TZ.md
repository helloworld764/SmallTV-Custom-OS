## 1. Краткое описание и цель

Создать собственную прошивку **Storm OS** для настольного мини-дисплея **GEEKMAGIC SmallTV-Ultra** на **ESP8266** с персонализируемыми экранами, постоянным индикатором доступности сервера, уведомлениями, мониторингом Debian-сервера, статусами Codex CLI, персонажем Null и игрой Tamagotchi. Устройство управляется физической кнопкой, веб-интерфейсом и единым Telegram-ботом. Основная бизнес-логика, хранение данных, обработка изображений, Telegram-интеграция и мониторинг выполняются на лёгком backend-сервере.

**Официальные названия:** прошивка и система — **Storm OS**, кратко **Storm**; веб-панель — **Storm Control Panel**; браузерный симулятор — **Storm Simulator**; будущий единый Telegram-бот — **Storm Bot**. На экране загрузки прошивки используется **Storm OS**; это правило именования не означает, что аппаратная прошивка уже реализована или проверена.

**Совместимость имён:** `SmallTV`/`SmallTV-Ultra` остаются названием физического устройства. GitHub-репозиторий `SmallTV-Custom-OS`, Python-пакет `backend`, внутренние идентификаторы `smalltv`, переменные `SMALLTV_`, API-маршруты, JSON-ключи, SQLite-таблицы, миграции и пути конфигурации сохраняются. Прежнее пользовательское название продукта — SmallTV Custom OS. Ребрендинг не меняет требования, архитектуру, безопасность и функциональность.

**Основной сценарий v1:** один SmallTV у владельца, backend на его старом ноутбуке с Debian 13 XFCE. **Расширяемость:** проектировать поддержку нескольких пользователей и устройств сразу, но не требовать VPS на старте. При подключении друзей — перенос центрального backend на VPS; при сохранении одного устройства — оставить Debian и позднее изолировать сервер от пентест-лаборатории.

**Базовый открытый проект для исследования:** https://github.com/iodn/geekmagic-tv-esp8266 . Это отправная точка, **не доказанная совместимость со всеми ревизиями SmallTV-Ultra**. Лицензию, схему выводов, загрузчик, Flash, дисплей, способ прошивки и возможность восстановления необходимо проверить.

## 3. Границы реализации

### 3.1. Обязательные функции первой полной версии (v1)

1. Прошивка с экраном часов/даты, погоды, Debian Monitor, Codex, отдельным экраном Null, отдельным экраном Tamagotchi.
2. BlackArch-inspired красно-чёрная тема по умолчанию, дополнительные темы, настройки оформления и пользовательские обои в рамках ресурсов устройства.
3. Физическая кнопка для переключения экранов; безопасная настройка Wi-Fi; локальная веб-страница устройства для базовых функций.
4. Постоянная маленькая точка состояния центрального backend **на каждом экране**; временные уведомления при переходах ONLINE/OFFLINE.
5. Система временных событий/оверлеев с приоритетами и возвратом к прежнему экрану.
6. Мониторинг Debian: CPU, температура (если доступна), RAM, SSD, uptime, доступность служб и предупреждения.
7. Статусы Codex CLI, работающего **на другом, основном Windows-ноутбуке**, через лёгкий Windows-компонент.
8. Один Telegram-бот Storm Bot: управление устройством и отдельный раздел Tamagotchi.
9. Tamagotchi: личный Null у владельца, общедоступные Pixel, Byte, Glitch, собственные питомцы через загрузку изображения; сохранение состояния на сервере.
10. Полная веб-панель Storm Control Panel для управления устройством, отдельная защищённая административная часть только владельцу.
11. Сервер на Debian: API, БД, служба бота, обработка медиа, мониторинг, логирование, автозапуск, резервное копирование.
12. OTA-обновление **только после проверки реального объёма Flash и безопасного способа восстановления**; если аппаратно безопасный OTA невозможен, документировать ограничение и применять надёжный проводной процесс.
13. Архитектурная готовность к нескольким устройствам/пользователям, хотя первый приёмочный сценарий — одно устройство.

### 3.2. Отложенные возможности (не реализовывать в v1 без отдельного решения)

- Отдельный Telegram-бот для Tamagotchi, создаваемый по желанию пользователя через BotFather и подключаемый к общей серверной логике.
- Полноценная интерактивная браузерная игра Tamagotchi с общим прогрессом между вебом, Telegram и SmallTV.
- Управление ИИ-агентом/Codex заданиями через Telegram — отдельный проект, **не включать автоматически**.
- Интеграция со статусом задач **официального приложения ChatGPT**: исследовательская, без обещания работоспособности; не подменять её событиями Codex.
- Массовое развёртывание на 20+ устройств, сложные анимации и дополнительные игровые механики.
- Специальная изоляция сервера от будущей пентест-лаборатории на первом этапе (базовые меры безопасности обязательны уже сейчас).

## 4. Архитектура

```text
ОСНОВНОЙ НОУТБУК / WINDOWS
  Codex CLI ──> Codex Monitor / интеграция событий
                       │ HTTPS/авторизованный API, heartbeat
                       ▼
СТАРЫЙ НОУТБУК / DEBIAN 13 (сначала)  ──> VPS (позже, при друзьях)
  Storm OS Backend (Python/FastAPI, пример рекомендуемого стека)
  ├── REST API / обмен событиями / device heartbeat
  ├── SQLite + миграции + резервные копии
  ├── Storm Bot (единый Telegram-бот: устройство + Tamagotchi)
  ├── Tamagotchi engine (вся игровая логика и состояние)
  ├── Monitor agent (CPU/RAM/SSD/температура/службы)
  ├── Event manager (приоритеты/дедупликация/TTL)
  ├── Media processor (валидация/уменьшение/конвертация)
  ├── Storm Control Panel (Web UI + Admin UI)
  └── Auth/RBAC/device registry
                       │ Wi-Fi / HTTP(S) с аутентификацией
                       ▼
SMALLTV-ULTRA / ESP8266
  ├── часы/NTP/дата и локальное отображение
  ├── экран погоды (кэш)
  ├── монитор Debian / Codex / Null / Tamagotchi
  ├── индикатор сервера на всех экранах
  ├── очередь уведомлений и восстановление экрана
  ├── физическая кнопка
  ├── локальный web UI / Wi-Fi provisioning
  └── OTA (если поддерживается безопасно)
```

**Разделение ответственности:** ESP рисует готовые экраны и не хранит общую игровую БД; Debian выполняет обработку и авторизацию. При переходе на VPS локальный монитор Debian и Windows Codex Monitor остаются отдельными агентами, которые могут отправлять события на удалённый backend. Если агент не запущен, его статус должен отображаться как OFFLINE/UNKNOWN, а не как исправный.

**Переносимость:** конфигурация через environment/config, никаких жёстко заданных LAN IP, путей или токенов в коде; отдельные миграции БД, экспорт/импорт данных, документированный процесс смены адреса backend на SmallTV без обязательной перепрошивки. Секреты не хранить в Git.

## 5. Прошивка: экраны и поведение

### 5.1. Общие требования

- Разрешение, контроллер дисплея, глубину цвета, доступный Flash/RAM, GPIO кнопки и тип загрузки **проверить на устройстве**.
- Дизайн: компактный, читаемый на маленьком экране; тема BlackArch Red (чёрный фон, красные акценты, контрастный текст) по умолчанию.
- На каждом экране виден **индикатор доступности центрального backend**: зелёный — свежая успешная проверка, жёлтый — проверка/устаревшие данные, красный — backend недоступен. Не утверждать, что красный доказывает физическое выключение ноутбука.
- Кнопка переключает экраны по заданному порядку. Поведение короткого/длинного нажатия и debounce определить после проверки аппаратной кнопки; не ломать заводской способ восстановления/прошивки.
- Экран и настройки не должны зависать из-за недоступности Wi-Fi, сервера, Telegram или погоды. Сетевые запросы с timeout и backoff, неблокирующий UI.
- Локальное время через NTP; корректная временная зона и переходы времени, когда применимо. При отсутствии NTP отображать последнее известное время с признаком возможной неточности.

### 5.2. Экран «Часы»

- Время, дата, день недели; варианты формата и оформление.
- Возможность выбрать стартовым экраном.
- Необязательные компактные погодные данные, если помещаются без потери читаемости.

### 5.3. Экран «Погода»

- Текущая погода, температура, краткое состояние и, при наличии источника, прогноз.
- Местоположение/город задаётся владельцем; не требовать GPS от устройства.
- Серверный кэш (ориентир 15–30 мин, с учётом условий API), отметка времени последнего обновления, поведение при недоступности поставщика.
- Выбор источника погодных данных после проверки условий бесплатного использования; не обещать бесплатность любого API.

### 5.4. Экран «Debian Monitor»

- CPU: общая загрузка; температура CPU при наличии корректного датчика.
- RAM: занято/всего; SSD: занято/всего, свободное место; uptime.
- Состояние API, Telegram-бота, базы, сетевого соединения; дополнительные показатели — только если их можно достоверно измерять.
- Температурные пороги, заполнение диска и прочие лимиты — конфигурируемые; сначала измерить штатные температуры N5000. Не применять произвольные 80/90 °C как аппаратно подтверждённые безопасные границы.
- Отдельный экран показывает мониторинг, а важные события выводятся автоматически поверх **любого** текущего экрана.

### 5.5. Экран «Codex»

- Статусы: `OFFLINE/UNKNOWN`, `IDLE`, `WORKING`, `DONE`, `ERROR` (и при необходимости `INTERRUPTED`).
- Анимация работы; краткое название задачи при доступности, длительность, время последнего события.
- `DONE` — завершение отслеживаемого задания/ответа, **не утверждение, что результат корректен**. `ERROR` — подтверждённая ошибка, а не просто отсутствие связи.
- При `DONE/ERROR` — приоритетное краткое уведомление с Null и возвратом на прежний экран.
- Официальный ChatGPT не входит в гарантируемые источники событий.

### 5.6. Экран «Null»

- **Null** — личный питомец владельца, именно написание `Null`, не `Nal`.
- Отдельный полноценный экран персонажа, не постоянная наклейка на каждом экране.
- Анимации idle/реакции, если позволяет ESP; образ согласовать с референсом владельца, когда он его предоставит.
- Null может использоваться как персонаж уведомлений Codex; это не делает экран Null частью Tamagotchi.

### 5.7. Экран «Tamagotchi»

- Отдельная игра, отдельный экран. Состояние и действия приходят с backend.
- Отображение персонажа, настроения, сна, голода/энергии и иных утверждённых игровых показателей.
- При отключении backend — кэш последнего состояния/локальная безопасная анимация; **не подтверждать игровые действия и не менять авторитетное состояние без сервера**.
- Точные игровые правила, скорость изменения показателей, баланс, последствия длительного отсутствия и частота обновления — отдельный согласуемый дизайн-документ до реализации механики.

## 6. Уведомления и индикация

### 6.1. Включение и выключение сервера

- При переходе `OFFLINE -> ONLINE` после подтверждённого восстановления связи: временный оверлей **«Сервер включён»** (ориентир 3–5 секунд), затем возврат на ранее открытый экран.
- При переходе `ONLINE -> OFFLINE` после нескольких неуспешных проверок/тайм-аута: **«Сервер выключен»**, затем возврат на прежний экран.
- Эти пользовательские фразы обозначают **доступность backend**, а не доказанный факт включения/выключения питания; при возможности в подробном статусе показывать «связь потеряна».
- При штатном выключении Debian можно заранее отправить событие shutdown, но нельзя полагаться только на него: при обрыве питания сервер ничего не отправит.
- Не показывать ложное «включён» при первом старте до первой успешной проверки; не спамить при кратких сбоях Wi-Fi. Использовать hysteresis, debounce, cooldown и дедупликацию.
- Индикатор в углу остаётся видимым **всегда**, включая уведомления, насколько позволяет компоновка.

### 6.2. Очередь событий

- Типы: `info`, `warning`, `critical`; приоритеты: критическая проблема > важное событие > обычное уведомление.
- Примеры: потеря сервера, перегрев, нехватка SSD, сбой службы, Codex DONE/ERROR.
- Оверлей временно прерывает экран, по завершении восстанавливает его; новые критические события могут прерывать обычные.
- Конфигурируемые TTL, частота повторов, подавление одинаковых событий, журнал на сервере.
- Не терять критические события при одновременном поступлении нескольких уведомлений; предусмотреть ограниченный буфер на ESP.
- При недоступности backend сам ESP обязан определить потерю связи по собственному опросу.

## 7. Оформление и медиа

**Веб-раздел Appearance / «Оформление»:**

- Готовые темы: `BlackArch Red` (по умолчанию), `Dark Blue`, `Purple`, `Light`; пользовательские цвета фона, текста и акцентов.
- Яркость, главный экран, порядок экранов, форматы часов, параметры уведомлений и видимости элементов (но **индикатор сервера нельзя полностью убрать**, если это нарушает согласованное обязательное поведение).
- Загрузка собственных обоев; сервер проверяет формат, размеры, лимит файла, декодирует и конвертирует в формат/размер, допустимый ESP. Не отправлять оригинальные тяжёлые PNG/JPEG без преобразования.
- Оптимизация статичных изображений и спрайтов, кэширование; ограничить число и объём медиа по фактическому Flash.
- Учитывать, что полноэкранные обои могут ухудшить читаемость; контраст/подложка для текста.
- В v1 **не обещать** произвольные GIF, видео, сложные альфа-эффекты или неограниченные пользовательские темы.

## 8. Tamagotchi: питомцы, создание, данные

### 8.1. Персонажи

- `Null` — **эксклюзивный личный питомец владельца**; не входит в общедоступный список по умолчанию.
- Общедоступные базовые: `Pixel` — белый пиксельный кот; `Byte` — зелёный слизень; `Glitch` — маленький фиолетовый цифровой призрак. Это выбранные концепты; финальные спрайты согласовать перед выпуском.
- Пользователь может создать и загрузить собственного питомца.
- У каждого пользователя свой питомец, показатели, история и прогресс; один пользователь не может менять чужие данные.

### 8.2. Создание собственного питомца через Telegram

1. Меню `Tamagotchi -> Мой питомец -> Создать своего`.
2. Бот выдаёт **единый шаблон промпта** с одним местом для описания.
3. Пользователь вставляет описание, генерирует изображение во внешнем ИИ и отправляет результат боту.
4. Сервер проверяет изображение (размер, MIME/сигнатура, декодирование, лимиты, безопасность), нормализует, создаёт подходящий спрайт и показывает превью.
5. Пользователь подтверждает; питомец сохраняется и отображается на SmallTV.
6. Если формат не подходит — понятная ошибка и предложение повторить; не принимать произвольные исполняемые файлы.

**Шаблон промпта для выдачи ботом:**

> Создай одного персонажа для пиксельной игры Tamagotchi на маленьком экране 240×240.  
> **Описание персонажа:** [ВСТАВЬ СЮДА ОПИСАНИЕ СВОЕГО ПИТОМЦА].  
> Стиль: качественный 2D pixel art, чёткие пиксельные контуры, ретро-игра, простой узнаваемый силуэт, выразительные глаза. Один персонаж целиком, вид спереди, по центру, квадратная композиция 1:1, персонаж занимает около 70% кадра. Без текста, интерфейса, посторонних предметов, теней на полу и фона. Прозрачный фон, если поддерживается. Изображение должно оставаться читаемым при уменьшении до 96×96. Сохрани единые пропорции для будущих анимационных состояний. Создай **одно** изображение в нейтральном состоянии, предпочтительно PNG.

**Примечание:** одинаковый промпт не гарантирует идентичный стиль разных генераторов; серверная нормализация обязательна. Размер 96×96 — предварительный ориентир, проверить на реальном дисплее. Дополнительные состояния (happy/sleep/sad) — после базового одиночного спрайта.

### 8.3. Логика игры

- Сервер является источником истины: кормление, сон, игра, настроение, прогресс.
- Действия идемпотентны там, где возможны повторы Telegram/API; защита от частого нажатия и гонок.
- Состояние хранится в SQLite транзакционно, с метками времени и восстановлением после рестарта.
- Не привязывать игровую механику к постоянно работающему экрану SmallTV.
- Будущая веб-игра должна использовать **тот же игровой движок и БД**, без параллельных несинхронизированных реализаций.

## 9. Storm Bot — Telegram-бот

**В v1 ровно один общий Telegram-бот**, обслуживающий устройства и Tamagotchi.

**Основное меню:** `Устройство`, `Tamagotchi`, `Настройки`, `Статус`.

**Устройство:** выбор привязанного устройства (если их несколько), смена экрана, яркость, базовые настройки, краткий статус и уведомления.  
**Tamagotchi:** выбор/создание питомца, кормление, игра, сон, состояние, загрузка собственного изображения, выдача ИИ-промпта.  
**Настройки:** только базовые параметры, не все административные возможности.  
**Статус:** доступность устройства/backend, последняя связь.

- Привязка Telegram user ID к учётной записи через одноразовый код/подтверждённую авторизацию.
- Проверка прав на **каждой** команде и callback, не только скрытие кнопок.
- Rate limiting, защита от повторных callback и обработка ошибок Telegram.
- Бот может быть недоступен при выключенном Debian; локальные функции SmallTV продолжают работать.

**Отложено:** пользователь через BotFather создаёт своего отдельного бота для Tamagotchi и привязывает токен к нашей системе. Сам BotFather создаёт оболочку бота, но **не устанавливает функции автоматически**. Реализовать только после оценки безопасного хранения токенов, ограничений Telegram, привязки владельца и обработки множества bot tokens.

## 10. Веб-интерфейсы и права

### 10.1. Storm Control Panel — полная веб-панель пользователя

- Управление экранами, кнопкой/порядком экранов, яркостью, Wi-Fi (в рамках безопасно реализуемого), темами, обоями, уведомлениями, настройками часов/погоды, питомцем, устройством и доступными обновлениями.
- Статусы устройства, версия прошивки, последняя связь, журнал основных событий, резервное/восстановление конфигурации при необходимости.
- Адаптивность для телефона и ПК; минимальная нагрузка на сервер.

### 10.2. Админ-панель владельца (Super Admin)

- Просмотр всех пользователей/устройств, привязок, версий прошивки, доступности, ошибок.
- Мониторинг Debian, служб, логов, резервных копий, глобальных настроек и политики обновлений.
- Управление правами и отзыв доступа; никакого доступа друзей к чужим устройствам или общим серверным настройкам.
- Желательно доступ только через VPN/приватный канал; защищённая аутентификация, MFA при доступности. Для публичной панели — HTTPS обязательно.

### 10.3. Локальная веб-страница ESP

- Минимальные функции: первоначальная настройка Wi-Fi/адреса backend, базовая диагностика и восстановление связи, если хватает памяти.
- Должна работать при недоступности Debian. Не пытаться переносить всю тяжёлую серверную веб-панель на ESP8266.
- Защитить режим первичной настройки от несанкционированного подключения; не держать открытый конфигурационный AP постоянно.

### 10.4. RBAC и мультитенантность

Роли: `super_admin` (владелец системы), `user` (свои устройства/питомцы); сервисные идентичности `device` и `agent` с ограниченными полномочиями. Устройства привязываются к владельцу, сервер проверяет права на каждый API-запрос. Не считать Telegram username безопасным идентификатором.

## 11. Backend и API

**Предлагаемый стек:** Python 3 + FastAPI, SQLite, systemd, библиотека Telegram-бота (выбрать при реализации), лёгкий HTML/CSS/JS frontend. Это предложение, не требование к конкретным версиям пакетов. Избегать ненужных сервисов (Redis, PostgreSQL, Kubernetes) на первом этапе.

### 11.1. Логические сущности

- `users`, `telegram_links`, `devices`, `device_credentials`, `device_settings`, `themes`, `media_assets`;
- `pets`, `pet_states`, `pet_actions`;
- `codex_agents`, `codex_runs`, `events`, `notifications`;
- `server_metrics`, `service_health`, `audit_log`, `schema_migrations`.

Хранить секреты отдельно и защищённо; не сохранять токены в открытых логах. Схему, связи и индексы уточнить до написания миграций.

### 11.2. Предварительный API-контракт (не финальные URL)

| Метод / маршрут (пример) | Назначение |
|---|---|
| `GET /api/v1/health` | Health backend (без утечки секретов) |
| `POST /api/v1/devices/enroll` | Привязка устройства по одноразовому коду |
| `GET /api/v1/devices/{id}/state` | Состояние/настройки для конкретного устройства |
| `POST /api/v1/devices/{id}/heartbeat` | Отметка связи/версия прошивки |
| `GET /api/v1/devices/{id}/events` | Получение событий с курсором/последовательностью |
| `POST /api/v1/agents/codex/events` | Авторизованные события Windows Codex Monitor |
| `POST /api/v1/agents/codex/heartbeat` | Доступность агента |
| `GET /api/v1/monitor` | Разрешённые метрики Debian |
| `GET/POST /api/v1/pets/...` | Состояние и игровые действия |
| `POST /api/v1/media/pets` | Загрузка и нормализация спрайта |
| `POST /api/v1/media/wallpapers` | Загрузка и нормализация обоев |
| `GET/PATCH /api/v1/settings/...` | Настройки пользователя/устройства |
| `GET /api/v1/admin/...` | Защищённые функции Super Admin |

Точные методы, тела, коды ошибок, схемы OpenAPI, курсоры, лимиты, TTL и модель аутентификации утвердить перед реализацией. Нельзя давать устройству право читать все пользовательские данные.

### 11.3. Обновления и периодичность

- Health устройства/сервера: ориентир **5–15 с** с адаптивным backoff; измерить влияние на ESP и сеть.
- Мониторинг метрик: ориентир **5–15 с** локально, реже для медленных датчиков.
- Погода: серверный кэш примерно **15–30 мин**, согласно API.
- События Codex: отправлять по событию + heartbeat, а не опрашивать весь Windows-процесс каждые миллисекунды.
- Tamagotchi: состояние по запросу/событию, периодическая синхронизация при необходимости.
- Предпочесть простой polling для первого прототипа; WebSocket/MQTT использовать только если доказана необходимость и совместимость.

## 12. Codex CLI на основном Windows-ноутбуке

**Критично:** Codex **не установлен на Debian-сервере**. Он запускается на основном ноутбуке Windows.

- На Windows реализовать лёгкий `Codex Monitor`/обёртку, который получает подтверждённые события `START`, `WORKING`, `DONE`, `ERROR`, `INTERRUPTED`, heartbeat и отправляет их в Debian API.
- Сначала исследовать документированные возможности конкретной установленной версии Codex CLI: хуки, события, логирование, режимы запуска. Не утверждать, что все интерактивные сессии можно отслеживать без обёртки.
- Если штатного надёжного event API нет — запускать отслеживаемые задачи через обёртку; объяснить пользователю границы покрытия.
- При выключенном Windows-ноутбуке или пропаже агента — `OFFLINE/UNKNOWN`; **не отправлять ложное DONE**.
- При нескольких задачах предусмотреть `run_id`, временные метки, состояние каждой и политику отображения активной задачи.
- Аутентификация агента отдельным токеном, TLS при передаче вне доверенной локальной сети, защита от повторной отправки событий.
- При переносе backend на VPS Windows-агент перенастраивается на новый адрес, сам Codex остаётся на Windows.

## 13. Безопасность

На первом этапе **не нужна специальная изоляция от пентест-лаборатории**, поскольку пользователь пока не запускает лабораторные мишени. Но обязательна базовая защита:

1. Серверные службы запускаются от отдельного непривилегированного системного пользователя, без постоянного root.
2. Секреты через ограниченные по правам файлы/environment; никогда не коммитить в Git.
3. Минимально необходимые открытые порты, firewall, закрытая по умолчанию админ-панель.
4. HTTPS для удалённого доступа; не открывать сырой API в интернет без аутентификации. Для дома предпочесть приватный туннель/VPN или защищённый gateway, если понадобится доступ извне.
5. Device provisioning с одноразовым кодом, уникальными credentials на устройство, возможностью отзыва/ротации.
6. RBAC и серверная проверка владения ресурсами; ограничение запросов и загрузок.
7. Валидация пользовательских изображений, защита от path traversal, decompression bombs и небезопасных декодеров.
8. CSRF/session-cookie меры для веба, безопасные заголовки, защита входа, журнал административных действий.
9. Обновления зависимостей, минимальные права, резервные копии и проверяемое восстановление.
10. Для OTA: проверка целостности и, если возможно, подлинности образа; защита от случайной прошивки неподходящей ревизии.

**Позднее, если сервер останется на Debian и начнутся пентест-лабы:** изолировать лабораторные сети и сервисы от SmallTV; при необходимости использовать отдельные аккаунты, firewall, Podman/VM с учётом 4 ГБ RAM. Не считать контейнеры полной защитой от вредоносной лабораторной нагрузки. Если изоляция слишком тяжёлая, лаборатории перенести на основной ноутбук.

## 14. Надёжность и эксплуатация Debian

- Службы через `systemd`: автозапуск, Restart=on-failure, зависимости, health checks, логирование и ограничение ресурсов по возможности.
- Debian может работать с выключенным экраном и закрытой крышкой **без перехода в сон** после проверки `systemd-logind` и XFCE Power Manager. Обеспечить вентиляцию, исправный блок питания, контролировать нагрев.
- При штатном выключении завершать запись БД, закрывать процессы, при возможности посылать предварительное событие; при аварийном выключении полагаться на транзакции и восстановление.
- SQLite: WAL по обоснованию, транзакции, миграции, проверка целостности; `synchronous=FULL` рассмотреть для критических данных с учётом производительности.
- Резервные копии БД делать согласованным способом (SQLite backup API / VACUUM INTO, а не простое копирование активного файла без WAL); хранить несколько версий, **включая копию вне ноутбука**.
- Сохранение прогресса Tamagotchi, учётных записей и привязок при перезапуске.
- Логи с ротацией, мониторинг заполнения SSD, проверка свободного места перед загрузкой медиа.
- Устройство должно переподключаться после восстановления Wi-Fi/API; локальные функции не зависят от работающего сервера.

## 15. Перенос на VPS и варианты дальнейшей эксплуатации

### Сценарий А: подключаются друзья

- После успешной работы на одном устройстве арендовать VPS, перенести **центральный backend, Telegram-бота, веб-панель, SQLite, медиа и пользователей**.
- Настроить HTTPS, DNS/адрес API, доступ устройств из разных домашних сетей, защищённые учётные записи.
- Windows Codex Monitor и (если нужен) монитор локального Debian остаются отдельными агентами, передающими данные на VPS; при полном освобождении ноутбука локальный Debian Monitor может быть отключён или заменён мониторингом VPS — согласовать поведение экрана.
- Проверить работу всех устройств, переключить адрес сервера, после чего остановить/удалить локальные службы и данные **только после проверенного переноса и резервной копии**.
- У друзей не требуется постоянно включённый ПК; требуется питание SmallTV, Wi-Fi и доступность VPS.

### Сценарий Б: только одно устройство

- Backend остаётся на старом Debian.
- Когда пользователь решит делать пентест-лабораторию, отдельно спроектировать изоляцию.
- При выключении Debian серверные функции SmallTV и Telegram недоступны; локальные часы/кнопка/кэш продолжают работать.

**Никаких обязательных платных сервисов в v1.** Использование VPS — отдельное будущее решение. Погодные API, туннели и иные сторонние сервисы выбирать с проверкой реальных лимитов и условий.

## 16.1. Разработка до доставки SmallTV и симулятор

**Решение:** не ждать доставки устройства. До получения аппаратного экземпляра можно исследовать исходники и лицензию, создать Git-репозиторий, разработать FastAPI/SQLite, мониторинг Debian, API-контракты, Telegram-бот, игровую логику, Windows Codex Monitor и веб-панель. **Не прошивать устройство и не считать совместимость проверенной** до физической проверки ревизии и безопасной процедуры восстановления.

Создать лёгкий **браузерный Storm Simulator с областью экрана 240×240** для SmallTV (отдельный инструмент разработки, не полноценная будущая веб-игра Tamagotchi). Он должен получать данные из того же API и позволять проверять экраны, индикатор соединения, очередь уведомлений, состояния питомца и Codex. Симулятор не заменяет испытаний на реальном ESP8266 и не гарантирует совместимость по RAM/Flash/производительности.

**Порядок до доставки:** аудит исходников → каркас проекта → минимальный backend и тесты → мониторинг и API → симулятор → Telegram/Tamagotchi и Windows Monitor по отдельным проверяемым задачам. После доставки: аудит устройства → безопасная минимальная прошивка → интеграция и ресурсные измерения → OTA только после проверки.

**Разработка с Codex CLI:** Codex работает на основном Windows-ноутбуке. В корне репозитория лежат `TZ.md` (требования) и `AGENTS.md` (правила работы агента). Codex должен читать оба файла, выполнять только явно поставленную задачу, запускать доступные проверки и фиксировать изменения. Изменения ТЗ требуют согласования владельца.

| Этап | Работа | Критерий готовности |
|---|---|---|
| 0. Аудит устройства и исходников | Ревизия SmallTV, лицензия, Flash/RAM, дисплей, GPIO, прошивка/восстановление, OTA | Документированы проверенные характеристики, риски и безопасный способ прошивки |

| 3. Базовая прошивка (после доставки; до неё — симулятор) | Часы, погода, кнопка, индикатор, Debian Monitor | Работает на реальном устройстве и не зависает при потере Wi-Fi |

- [ ] Устройство запускается, подключается к Wi-Fi, отображает время/дату, переключает экраны кнопкой.
- [ ] При выключенном backend локальные часы/кнопка/кэш доступны, UI не зависает.
- [ ] Индикатор на **каждом** экране корректно меняет зелёный/жёлтый/красный состояния.
- [ ] После подтверждённой потери связи показывается «Сервер выключен» один раз; после восстановления — «Сервер включён», затем возврат к прежнему экрану.
- [ ] Краткий сетевой сбой не вызывает лавину уведомлений.
- [ ] Debian Monitor показывает достоверные значения, недоступные датчики помечены как N/A, а не вымышленные.
- [ ] Критический серверный алерт прерывает текущий экран и возвращает его после закрытия.
- [ ] Codex на **Windows** отправляет WORKING/DONE/ERROR; при аварийном выключении Windows нет ложного DONE.
- [ ] Null имеет отдельный экран и используется в согласованных уведомлениях.
- [ ] Telegram-бот управляет только привязанным устройством; Tamagotchi доступен отдельным разделом того же бота.
- [ ] Pixel/Byte/Glitch доступны обычному пользователю; Null не выдан как общедоступный питомец.
- [ ] Бот выдаёт единый промпт, принимает корректное изображение, отклоняет небезопасное/неподдерживаемое, показывает результат на устройстве.
- [ ] Состояние Tamagotchi сохраняется после перезапуска сервера.
- [ ] Темы и обои можно менять через веб, настройки сохраняются.
- [ ] Super Admin видит общие настройки; обычный пользователь не может получить чужие данные даже прямым API-запросом.

### Надёжность и безопасность

- [ ] `systemd` автоматически поднимает backend после перезагрузки Debian.
- [ ] Штатное и внезапное отключение не приводят к повреждению БД в проверенных сценариях.
- [ ] Резервная копия восстановлена на чистой тестовой установке.
- [ ] Устройство переподключается после перезапуска Wi-Fi и сервера.
- [ ] OTA либо безопасно протестирован, либо явно отключён и заменён документированной процедурой прошивки.
- [ ] В репозитории и логах нет реальных токенов, паролей и приватных ключей.
- [ ] Неавторизованные запросы к API, admin и чужим устройствам отклоняются.
- [ ] Проведён **72-часовой** непрерывный тест при обычной нагрузке; зафиксированы RAM, CPU, температуры, ошибки и переподключения (72 часа — целевой тест, не гарантия безотказности).

## 19. Ключевые риски и открытые вопросы

1. **Аппаратная ревизия SmallTV-Ultra:** подтвердить контроллер дисплея, точную Flash, доступную RAM, распиновку, способ прошивки, резервное восстановление и совместимость с исходным проектом.
2. **OTA:** поддерживает ли разметка Flash безопасное обновление? Возможен ли откат? Не обещать dual-bank без проверки.
3. **Codex CLI:** какие официально поддерживаемые события доступны в установленной Windows-версии? Как отличить завершение ответа от завершения процесса?
4. **Null:** нужен референс изображения от владельца для точного дизайна спрайта.
5. **Погодный сервис:** выбрать источник, бесплатные лимиты, политику кэширования.
6. **Спрайты/обои:** измерить допустимые размеры, количество кадров и доступную Flash.
7. **Сетевая схема:** локальный HTTP в доверенной LAN или TLS через gateway; как обеспечивать первичную настройку и безопасную смену сервера.
8. **Геймдизайн Tamagotchi:** точные показатели, формулы, частота изменения, наказания/награды, сохранение прогресса.
9. **Физическая кнопка:** проверить число кнопок и функции заводской прошивки, не лишить пользователя recovery.
10. **Управление питанием Debian:** поведение закрытой крышки, вентиляция, аккумулятор, возможность ограничения заряда на данной модели.
11. **VPS:** выбрать тариф и способ миграции только при реальной необходимости, без заранее обещанных цен и производительности.

## 20. Инструкция следующему ИИ-чату / разработчику

**Контекст:** владелец изучает информационную безопасность, работает с Windows + Codex CLI на основном ноутбуке и Debian 13 XFCE на старом ASUS N5000/4 ГБ. SmallTV-Ultra ещё ожидается. Проект пока в стадии ТЗ, начинать реализацию по команде пользователя.

**Правила продолжения:**

1. Прочитать документ целиком и считать его текущим источником согласованных требований.
2. Не путать два ноутбука: **Codex на Windows; backend на Debian**.
3. Не путать Null с Nal и не включать Null в общедоступную тройку Pixel/Byte/Glitch.
4. Один Telegram-бот в v1; отдельные личные боты и браузерная Tamagotchi-игра — позже.
5. Не переносить сервер на VPS заранее: сначала один SmallTV на Debian; решение о VPS зависит от приглашения друзей.
6. Пока не строить сложную изоляцию от лаборатории, но не отменять базовую безопасность.
7. Не обещать мониторинг официального ChatGPT без проверяемого API.
8. Проверять железо и лицензию исходного проекта до прошивки; всегда сохранять возможность восстановления.
9. Предлагать небольшие проверяемые шаги, команды с объяснением, контрольные точки и откат. Не удалять данные и не менять работающие сервисы без подтверждения.
10. Любые новые решения фиксировать в changelog ТЗ; разделять «подтверждено», «предложено» и «требует проверки».
