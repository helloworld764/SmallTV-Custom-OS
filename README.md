# Storm OS

**Storm OS** (кратко **Storm**) — система и прошивка для GEEKMAGIC SmallTV-Ultra.
Веб-панель — **Storm Control Panel**, симулятор 240×240 — **Storm Simulator**,
будущий единый Telegram-бот — **Storm Bot**. На экране загрузки прошивки используется Storm OS.
Реальная прошивка пока не реализована. Первый локальный этап Storm Bot
(привязка аккаунта, меню, город и настройки уведомлений) описан в
[docs/storm-bot.md](docs/storm-bot.md). Живое подключение Telegram требует
локального токена и отдельной проверки; прочие источники уведомлений остаются
следующими этапами. Часовой сон и уведомление о пробуждении:
[docs/timed-pet-sleep.md](docs/timed-pet-sleep.md).
Карточка питомца, создание и уход в боте реализованы:
[docs/bot-pet-care.md](docs/bot-pet-care.md).

Техническое имя GitHub-репозитория остаётся `SmallTV-Custom-OS`.
Пакет `backend`, идентификаторы `smalltv`, переменные `SMALLTV_`, API, JSON-ключи,
таблицы SQLite, миграции и пути конфигурации сохранены для совместимости.

FastAPI backend, SQLite, веб-панель управления и симулятор дисплея 240×240.
Требования проекта находятся в `TZ.md`, правила работы — в `AGENTS.md`.
Изменения требований и правил требуют согласования владельца; ребрендинг отражён в ТЗ v1.2.

Weather city preferences, API behavior and provider constraints: [docs/weather.md](docs/weather.md).

## Структура

```text
backend/app/      API, конфигурация и точка запуска
backend/migrations/  нумерованные SQL-миграции
firmware/         описание будущего аппаратного компонента, без прошивки
assets/pets/     исходники, приватный просмотр и обзорные листы
web/simulator/   HTML/CSS/JS симулятор и три публичных кадра каталога
web/panel/       локальная веб-панель: вход, устройства и настройки
codex-monitor/   read-only задачи Codex, парсер, outbox/heartbeat и DPAPI
docs/            архитектура и границы первого этапа
tests/           Python API/config и JavaScript connection tests
```

Название `codex-monitor/` и общие `tests/` выбраны по текущему заданию владельца.
Backend предназначен для Debian; локальная разработка и Codex остаются на Windows.
SQLite хранит базовый реестр пользователей, устройств и настроек.
Добавлены серверные сессии и API с проверкой владельца устройства.
Добавлен первый серверный движок Tamagotchi: профиль, имя, уход, показатели,
исчезновение 72+24 часа и семантические реакции API: [docs/pet-engine.md](docs/pet-engine.md).
Игровой UI, Telegram, медиа, OTA, реальная прошивка и постоянный монитор всех сессий
ещё не реализованы. Социальные функции согласованы после основных в ТЗ v1.3.
Внешний вид всех четырёх персонажей одобрен владельцем. Три общих питомца
подключены к авторизованному превью Tamagotchi в Storm Simulator; оно читает
реакции из API. Null остаётся личным и не публикуется по HTTP. Подробности и
ограничения сетки кадров: [docs/pet-display-preview.md](docs/pet-display-preview.md).
Это превью не является браузерной игрой или проверкой прошивки.

## Windows (PowerShell)

Нужен Python 3.11+ с модулем venv. Из корня проекта:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements-dev.txt
.\.venv\Scripts\python.exe -m backend.app
```

Активация окружения и изменение ExecutionPolicy не требуются.
Если `py` недоступен, используйте полный путь к установленному `python.exe`.
Для запуска без тестовых зависимостей устанавливайте `backend/requirements.txt`.

## Debian (ручной локальный запуск)

Нужны Python 3.11+, pip и поддержка venv; установка системных пакетов здесь не выполняется.
Из корня проекта, от обычного пользователя:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements-dev.txt
.venv/bin/python -m backend.app
```

Это инструкция для разработки, а не развёртывание: systemd, firewall и питание не меняются.

## Backend и симулятор

После запуска откройте:

- `http://127.0.0.1:8000/health` → `{"status":"ok"}`
- `http://127.0.0.1:8000/panel/` → Storm Control Panel
- `http://127.0.0.1:8000/simulator/` → Storm Simulator, дисплей 240×240
- `http://127.0.0.1:8000/docs` → OpenAPI

Симулятор обслуживается backend и использует относительный `/health`, без CORS
и отдельного сервера. Не открывайте HTML через `file://`.
По умолчанию сервер слушает только `127.0.0.1`; доступ из LAN не настраивается.
Для просмотра симулятора при запуске на Debian откройте браузер на самом Debian.

Часы — локальное время браузера, не эмуляция NTP/RTC ESP8266.
Автономный `/simulator/` не требует входа. В настройках зарегистрированного
устройства в панели есть ссылка «Открыть превью устройства»:
`/simulator/?device=<id>` читает сохранённые настройки через защищённый API.
Применяются тема, яркость содержимого и стартовый экран. Индикатор backend
остаётся видимым даже при нулевой яркости превью.
Неподключённые экраны (погода, мониторинг, Codex и Null) явно помечены,
без вымышленных показателей. Tamagotchi показывает питомца и его API-состояние,
если он создан у вошедшего пользователя; игровые действия и браузерная игра не добавлены.

Превью проверяет настройки после успешной проверки backend, без параллельных
запросов. Изменения из панели появятся в следующем цикле опроса. При сетевом сбое
последние настройки сохраняются только в памяти с отметкой устаревания; при
401/403/404 они сбрасываются. Cookie общая с панелью, токены в URL не передаются.
Реестр сам не заполняется: при отсутствии устройств панель остаётся пустой.

Индикатор всегда виден, в том числе во время временного уведомления:

- жёлтый — первоначальная проверка, ошибка или данные старше 15 секунд;
- зелёный — свежий успешный ответ API;
- красный — три ошибки подряд.

Проверки идут последовательно: timeout 2,5 с, обычный интервал 5 с,
после ошибок паузы 10/20/30 с. Подтверждение потери связи занимает примерно
30–45 с в активной вкладке; фоновые вкладки могут проверяться реже.
Первый успешный ответ не вызывает уведомление о включении.
Смена подтверждённого состояния вызывает уведомление на 4 секунды;
короткий сбой не вызывает пары уведомлений. Красный означает недоступность API,
а не доказанное отключение питания. В авторизованном превью выбранного устройства
добавлены короткие уведомления Codex DONE/ERROR/INTERRUPTED с TTL, приоритетами
и защитой от повторов: [docs/simulator-notifications.md](docs/simulator-notifications.md).
Это проекция журнала для симулятора; общей серверной очереди и физической доставки пока нет.

Проверка вручную: остановите сервер через Ctrl+C, оставьте вкладку открытой,
дождитесь красного индикатора и снова запустите сервер. Связь восстановится
автоматически, часы продолжают работать во время отключения.

## Конфигурация

Можно скопировать `.env.example` в `.env` в корне, если `.env` ещё не существует.
Переменные окружения имеют приоритет над `.env`. Все команды выполняются из корня.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SMALLTV_HOST` | `127.0.0.1` | Адрес прослушивания |
| `SMALLTV_PORT` | `8000` | Порт 1–65535 |
| `SMALLTV_LOG_LEVEL` | `info` | critical/error/warning/info/debug |
| `SMALLTV_DB_PATH` | `data/smalltv.sqlite3` | Файл SQLite, относительный путь от рабочей папки или абсолютный |
| `SMALLTV_COOKIE_SECURE` | `false` | `false` для локального HTTP; `true` для будущего HTTPS |
| `SMALLTV_SESSION_TTL_SECONDS` | `43200` | Срок сессии в секундах, 300–86400 |
| `SMALLTV_AGENT_STALE_SECONDS` | `30` | Через сколько секунд heartbeat устаревает, 10–3600 |
| `SMALLTV_AGENT_OFFLINE_SECONDS` | `90` | Тайм-аут связи агента, 15–86400; больше stale |
| `SMALLTV_DEVICE_STALE_SECONDS` | `30` | Устаревание heartbeat устройства, 10–3600 |
| `SMALLTV_DEVICE_OFFLINE_SECONDS` | `90` | Тайм-аут устройства, 15–86400; больше device stale |

Пример смены порта на Windows:

```powershell
$env:SMALLTV_PORT = '8123'
.\.venv\Scripts\python.exe -m backend.app
```

На Debian:

```bash
SMALLTV_PORT=8123 .venv/bin/python -m backend.app
```

Health проверяет только работоспособность процесса API. Он не проверяет устройство,
БД, сеть, Telegram или Windows. Ответ не содержит конфигурацию и секреты.

## SQLite и миграции

При запуске backend создаёт родительскую папку БД и применяет миграции из
`backend/migrations/`. Если база недоступна или история миграций не совпадает
с исходниками, запуск завершается ошибкой. Отдельная установка SQLite не нужна:
используется встроенный Python-модуль `sqlite3`.

В базе находятся реестр, локальные аккаунты, хеши сессий, лимиты входа и журнал действий.
Автоматических пользователей, паролей и демонстрационных устройств нет.
API чтения устройств и изменения настроек требует входа и проверяет владельца.
Публичная регистрация пользователей отсутствует. Программный протокол привязки
клиента устройства через одноразовый код, его отдельный ключ и отзыв доступа
описаны в [docs/device-enrollment.md](docs/device-enrollment.md).
Мастера привязки в панели и проверки физического устройства пока нет.
Добавлены device heartbeat и чтение UNKNOWN/ONLINE/STALE/OFFLINE по серверному
времени: [docs/device-presence.md](docs/device-presence.md). Чтение настроек,
проверка health и браузерный симулятор не отправляют heartbeat за устройство.
Для будущего Windows Codex Monitor добавлены отдельные регистрации и ключи
агентов: [docs/agent-identities.md](docs/agent-identities.md). Добавлены серверный
приём heartbeat и состояние связи UNKNOWN/ONLINE/STALE/OFFLINE по серверному времени.
Сервер принимает упорядоченные события START/WORKING/DONE/ERROR/INTERRUPTED с run_id
и защитой от повторов: [docs/codex-events.md](docs/codex-events.md). Это собственный
протокол; явно запускаемый Windows-мост уже получает реальные события exec JSONL.
Постоянное наблюдение за всеми интерактивными сессиями не реализовано.
Пользовательские cookie, device-
и agent-ключи не заменяют друг друга.

Проверить доступность CLI в обычном Windows PowerShell можно без запуска заданий:
`.\.venv\Scripts\python.exe codex-monitor/check_cli.py`. Утилита вызывает только
`--version`/`exec --help` и выводит безопасный JSON-отчёт. Эта диагностика сама
не запускает мониторинг. Исследование источника событий: [docs/codex-cli-research.md](docs/codex-cli-research.md).
Автономный парсер и его границы: [docs/exec-parser.md](docs/exec-parser.md).
Сам модуль парсера не запускает Codex/сетевую отправку; обёртка использует его
и для реальных явно запускаемых задач CLI 0.167.0.
Один реальный тест в отдельной временной папке можно запустить через
`.\.venv\Scripts\python.exe codex-monitor/smoke_exec.py --run`;
это уже задача Codex с использованием его обычных лимитов, не просто справка.
Условия запуска и безопасный JSON-отчёт: [docs/exec-smoke.md](docs/exec-smoke.md).
Локальная отправка нормализованных событий и heartbeat с устойчивой очередью
и DPAPI-хранилищем ключа: [docs/local-monitor.md](docs/local-monitor.md).
Мост поддерживает run-smoke и run-task, без постоянной службы и подключения к Debian.
Добавлена обёртка для явно запускаемых read-only задач:
`.\.venv\Scripts\python.exe codex-monitor/local_monitor.py run-task --cwd . --show-answer`.
Задание вводится скрыто и передаётся в stdin, а не в аргументы или очередь.
Правила завершения, Ctrl+C и приватности: [docs/task-runner.md](docs/task-runner.md).
Сначала проверить DPAPI без реального ключа:
`.\.venv\Scripts\python.exe codex-monitor/local_monitor.py check-key-store`.

Повторный запуск сохраняет записи и не повторяет применённые миграции.
База в `data/`, журналы SQLite, `.env` и тестовые файлы исключены из Git.
Не удаляйте БД для повторного запуска или изменения схемы.
Для нестандартного пути за пределами `data/` используйте расширение `.sqlite3`
или добавьте этот путь в локальные исключения Git.

Пример отдельного файла на Windows:

```powershell
$env:SMALLTV_DB_PATH = 'data/development.sqlite3'
.\.venv\Scripts\python.exe -m backend.app
```

На Debian:

```bash
SMALLTV_DB_PATH=data/development.sqlite3 .venv/bin/python -m backend.app
```

Подробности схемы и правила будущих миграций: [docs/database.md](docs/database.md).

## Резервное копирование SQLite

Из корня проекта на Windows:

```powershell
.\.venv\Scripts\python.exe -m backend.app.manage backup-db
.\.venv\Scripts\python.exe -m backend.app.manage verify-backup --source backups/manual-copy.sqlite3
.\.venv\Scripts\python.exe -m backend.app.manage restore-db --source backups/manual-copy.sqlite3 --output data/restored-check.sqlite3
```

В последних двух командах замените `manual-copy.sqlite3` на фактическое имя копии,
показанное первой командой. Для явного имени используйте `backup-db --output
backups/manual-copy.sqlite3`. При повторном запуске существующий файл не заменяется.
Источник копируется через SQLite Backup API, а результат проверяется.
Восстановление создаёт только новый файл и отзывает сессии в нём; рабочая БД,
`.env` и работающий backend автоматически не переключаются.
Копии содержат чувствительные данные, не зашифрованы и исключены из Git.
Подробные инструкции, ограничения и хранение вне ноутбука: [docs/backups.md](docs/backups.md).
Карта оставшихся требований и порядок согласования будущих функций: [docs/roadmap.md](docs/roadmap.md).

## Первый администратор и вход

Остановите backend через Ctrl+C. В корне проекта выполните на Windows:

```powershell
.\.venv\Scripts\python.exe -m backend.app.manage create-admin --username owner
.\.venv\Scripts\python.exe -m backend.app
```

Для локальной разработки на Debian:

```bash
.venv/bin/python -m backend.app.manage create-admin --username owner
.venv/bin/python -m backend.app
```

Пароль вводится дважды скрыто, минимум 12 символов. Не помещайте его в команду,
`.env`, Git или сообщения чата. Команда создаёт только первого администратора;
повторное выполнение при существующем администраторе завершается отказом.
При отсутствии терминала со скрытым вводом команда отказывается читать пароль.
Миграция 0002 добавляется автоматически; базу удалять не нужно.

Откройте `/panel/` и войдите с логином, указанным после `--username`, и созданным
паролем. Например, команда выше создаёт логин `owner`. В новой БД список устройств
пуст; панель не добавляет демонстрационные записи.

В панели доступны выход, обновление списка, выбор устройства, яркость, тема и
стартовый экран. Сессия восстанавливается при обновлении страницы. Истечение
сессии возвращает форму входа; ошибка связи не считается успешным сохранением.
При неоднозначном результате сохранения перечитайте настройки с сервера.
Несохранённые изменения защищены от переключения устройства, обновления списка
и выхода: сначала сохраните их или нажмите «Отменить изменения».
Обновление списка сохраняет выбранное устройство, если оно есть на загруженной странице.
Пароль не сохраняется в браузерном хранилище; CSRF-токен остаётся в памяти страницы.
Краткая инструкция первого входа также доступна по `/panel/help.html`.

Кнопка солнца/луны в правом верхнем углу переключает светлую/тёмную тему сайта:
панели, справки и страницы симулятора. Выбор сохраняется в этом браузере и
синхронизируется между открытыми вкладками. В localStorage хранится только
настройка `storm.site-theme`; при запрете хранилища переключение работает до
перезагрузки. Тема сайта не меняет сохранённую тему экрана устройства.
Дополнения к плану питомцев, бота и оформления:
[docs/functions-for-approval.md](docs/functions-for-approval.md).

Для дополнительной ручной проверки API можно использовать `/docs`:

1. В `POST /api/v1/auth/login` выберите Try it out, задайте заголовок
   `x-smalltv-client` = `web`, укажите свой логин и пароль в JSON и выполните запрос.
2. Cookie сессии устанавливается браузером автоматически. `GET /api/v1/auth/session`
   возвращает текущего пользователя и `csrf_token`.
3. `GET /api/v1/devices` возвращает доступные устройства. В новой БД список пуст:
   устройств и тестовых аккаунтов команда не создаёт.
4. Для `PATCH /api/v1/devices/{device_id}/settings` и `POST /api/v1/auth/logout`
   задайте заголовок `x-csrf-token` из ответа текущей сессии.

Вход и выход не требуются для публичных `/health` и `/simulator/`.
Изменение настроек сохраняет их в БД и применяется в превью выбранного устройства;
оно ещё не управляет реальным SmallTV. Контракты: [docs/auth.md](docs/auth.md).

## Автоматические тесты

Windows:

```powershell
.\.venv\Scripts\python.exe -m pytest
node --test tests/simulator.test.mjs tests/panel.test.mjs tests/branding.test.mjs tests/site-theme.test.mjs tests/pet-display.test.mjs
```

Debian:

```bash
.venv/bin/python -m pytest
node --test tests/simulator.test.mjs tests/panel.test.mjs tests/branding.test.mjs tests/site-theme.test.mjs tests/pet-display.test.mjs
```

Node.js 20+ нужен только для JavaScript-тестов; симулятор работает в современном
браузере без Node.js. Тесты проверяют API, конфигурацию, статические файлы,
потерю связи, восстановление, подавление кратких сбоев и ошибки ответов API.
SQLite-тесты работают с отдельными временными файлами: проверяют миграции,
сохранение после перезапуска, связи, ограничения и откат транзакций.
Рабочую БД тесты не используют.

При наличии Node.js 20+ pytest дополнительно запускает настоящий HTTP-тест:
JavaScript-клиент панели → авторизация → SQLite → модель превью симулятора → выход.
Он использует временные аккаунты/устройства и отдельный loopback-порт, останавливает
тестовый сервер сам и не обращается к Debian или рабочему порту 8000.
Без Node.js этот тест помечается skipped; остальные Python-тесты продолжают работать.

Зависимости заданы допустимыми диапазонами. Полного lock-файла пока нет;
результаты проверки конкретного окружения указаны в `docs/verification.md`.
Сторонний firmware-код не скопирован. Лицензия всего проекта пока не выбрана.
