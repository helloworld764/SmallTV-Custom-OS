# Storm OS — локальный мост Codex → backend

Добавлена отправка событий проверенного smoke-запуска в **локальный** backend
Windows. Это ещё не постоянный Monitor произвольных заданий/интерактивных сессий,
служба или подключение к Debian. Владелец подтвердил один штатный поток CLI
0.167.0: status=verified, exit_code=0, parser_outcome=DONE. Реальные ошибки и
прерывания CLI пока покрыты только синтетическими тестами.
Владелец также подтвердил dpapi_available, key_saved и реальный run-smoke:
status=delivered, connected=true, pending=0, exec.status=verified.
Для новых явно запускаемых read-only задач добавлена отдельная команда
[run-task](task-runner.md) со скрытым вводом, stdin и обработкой прерывания.

## Сначала проверить защиту ключа

Из корня проекта в обычном PowerShell, без настоящего ключа:

```powershell
.\.venv\Scripts\python.exe codex-monitor/local_monitor.py check-key-store
```

Ожидается `{"status":"dpapi_available"}`. Команда шифрует/расшифровывает случайные
байты в памяти, не обращается к модели/API и не создаёт файл ключа. В среде агента
Windows DPAPI вернула OS code 2; реальный тест там skipped, а не успешен. При
dpapi_unavailable не вводить настоящий ключ; прислать только безопасный JSON.

Ключ хранится в `secrets/storm-agent.dpapi` через current-user Windows DPAPI, без
LOCAL_MACHINE и без незашифрованного запасного варианта. Зашифрованы token,
agent_id и base_url. При недоступной DPAPI запись запрещается. См.
[Microsoft CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata).
Другой код того же Windows-пользователя может расшифровать такой файл; в памяти
работающего клиента ключ находится открыто. ACL системы не меняются.

## Настройка локального агента

1. Запустить backend в отдельном PowerShell:
   `.\.venv\Scripts\python.exe -m backend.app`.
2. В `/docs` войти существующим аккаунтом через POST `/api/v1/auth/login`,
   с `x-smalltv-client: web`. Пароль вводить локально, не в чат/командную строку.
   Cookie устанавливается автоматически; из ответа взять csrf_token.
3. В POST `/api/v1/agents/codex` передать `x-csrf-token` и JSON
   `{"name":"Windows local bridge"}`. Получить agent_id и однократно показанный
   token. Не присылать token в чат и не помещать его в Git/URL/аргументы команд.
4. После успешного check-key-store выполнить, заменив AGENT_UUID полученным UUID:

```powershell
.\.venv\Scripts\python.exe codex-monitor/local_monitor.py init-key --agent-id AGENT_UUID
```

В скрытый запрос `Agent key (hidden)` вставить выданный ключ. Если скрытый ввод
невозможен, команда отказывает. Существующий файл не заменяется. По умолчанию
привязка к http://127.0.0.1:8000; другой локальный порт задаётся через
`init-key --url http://127.0.0.1:8123`.

Поддерживаются только HTTP и буквальные 127.0.0.1/[::1] с явным портом, без
path/query/userinfo. localhost/DNS, LAN, Debian и публичные адреса запрещены.
Прокси окружения отключены, HTTP-редиректы не выполняются. Удалённый транспорт
с TLS — отдельный этап.

## Запуск и восстановление отправки

```powershell
.\.venv\Scripts\python.exe codex-monitor/local_monitor.py run-smoke
.\.venv\Scripts\python.exe codex-monitor/local_monitor.py status
.\.venv\Scripts\python.exe codex-monitor/local_monitor.py flush
```

run-smoke — одна настоящая задача Codex с обычной авторизацией/лимитами CLI,
в прежнем изолированном read-only профиле. START записывается при начале хода,
конечное событие — только после согласованного завершения. Ошибка outbox
останавливает отслеживаемый процесс с delivery_error, без вымышленного DONE.
До запуска нужны два свободных места. Для одной outbox команды run-task,
run-smoke и flush теперь взаимно исключаются; второй процесс получает already_running.

Heartbeat отправляется примерно каждые 10 секунд, пока работает мост. Это
доступность клиента-моста, не доказательство работы Codex/питания ПК. После выхода
сервер определяет STALE/OFFLINE по TTL. Heartbeat не сохраняется для поздней
доставки. Последовательные HTTP-запросы имеют timeout 2,5 с; в одном цикле возможны
identity/heartbeat/событие, поэтому сеть может замедлять чтение stdout. Буферы
ограничены, прежние лимиты smoke-потока сохранены.

status читает локальную очередь без HTTP/модели. flush не запускает Codex:
проверяет identity, отправляет текущий heartbeat и ожидает очередь/связь до 15 с
плюс начатый HTTP-запрос. Повторить можно вручную. Пустая очередь при недоступном
backend не выдаётся за delivered. delivered означает отсутствие ожидающих
событий и подтверждённый heartbeat; результат задания отдельно в exec.status.
pending/unavailable/blocked/exec_not_verified не означают успеха. В отчёте нет
ключей, произвольных ответов сервера и текстов Codex.

## Очередь и повторы

Отдельный файл `data/codex-monitor/outbox.sqlite3`, не серверная smalltv.sqlite3.
Он привязан к agent_id и каноническому адресу. Другой агент/адрес или посторонняя
БД отклоняются без удаления данных. Глобальные параметры задаются **перед**
подкомандой: `--key-file secrets/another.dpapi --outbox data/codex-monitor/another.sqlite3`.

Хранятся только пять полей нормализованного события, без ключа/prompt/ответа/stderr.
SQLite synchronous=FULL, enqueue и подтверждение транзакционные. Лимит — 1000
ожидающих записей. Записи удаляются только после совпадения event_id/run_id/sequence
и duplicate в подтверждении API. После потери ответа/рестарта повторяется то же
тело с прежним event_id. FIFO: проблемная первая запись блокирует последующие,
а не пропускается. Автоматического удаления переполненной/заблокированной очереди нет.

Сеть/408/5xx: паузы 1/2/4/.../30 с. 429 с численным Retry-After учитывается до
300 с; 429 без срока означает квоту и блокирует цикл. 401/403, конфликт и неверный
ответ останавливают отправку, сохраняя данные. Новый flush явно пробует снова;
backoff пока в памяти. Планировщика/фоновой службы нет.

Для ротации использовать серверную rotate, сохранить новый ключ в другом DPAPI-файле
с тем же agent_id/адресом и указать его с существующей очередью. Автоматической
замены ключей/очистки конфликтов нет. После restore серверной БД старые credentials
отзываются. Историческая доставка DONE не доказывает текущую работу Codex; будущим
уведомлениям нужны TTL. UI и доставка событий на SmallTV не добавлены.

При аварии до записи наблюдения оно может остаться UNKNOWN. Восстановления парсера
из приватных rollout нет. Устойчивость относится к успешно записанным событиям,
а не к ещё не наблюдавшемуся завершению. DPAPI-файлы и SQLite исключены из Git.

## Проверка очереди при отключении API

Автоматический воспроизводимый тест из корня проекта:

```powershell
.\.venv\Scripts\python.exe -m pytest tests/test_monitor_delivery.py -k real_api_outage -q
```

Используются отдельная временная серверная БД, outbox, случайный программный ключ
и собственный loopback-порт. Источник — локальный Python-процесс с синтетическим
JSONL, без запуска Codex/модели. Рабочие сервер, ключ, очередь и порт 8000 не участвуют.

Четыре сочетания проверяют подтверждённое завершение/неподтверждённый EOF и
обычное восстановление/потерю ACK после записи. При отключённом API события
сохраняются только в outbox; сервер не получает вымышленный статус. Затем сервер
запускается и клиент пересоздаётся из сохранённой очереди. В сценарии потери ACK
сервер успевает записать START, ответ теряется, затем API действительно останавливается
и заново запускается на прежнем адресе с той же БД. Клиент повторяет прежний event_id.

После восстановления все исходные event_id/run_id/sequence/kind/occurred_at совпадают
с серверными, число записей равно числу исходных событий, outbox пуст. Для
подтверждённого окончания итог DONE; для EOF без конечного события — WORKING с
обновлённой связью, без ложного DONE/ERROR. Это проверка очереди и HTTP-протокола
на изолированном сервере; отключение рабочего экземпляра владельца этим тестом
не проверяется.
