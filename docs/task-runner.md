# Storm OS — явно запускаемые задачи Codex

Добавлена команда `run-task` для одного нового read-only процесса Codex CLI.
Она использует существующие DPAPI-ключ, loopback backend, очередь и heartbeat.
Не отслеживает чужие/уже открытые сессии, IDE, приложение ChatGPT и не запускается
автоматически. Debian, службы, веб-панель, бот, Tamagotchi и прошивка не меняются.

## Запуск

Из корня проекта, после настройки [локального моста](local-monitor.md):

```powershell
.\.venv\Scripts\python.exe codex-monitor/local_monitor.py run-task --cwd . --show-answer
```

В `Task (hidden, single line):` ввести своё **однострочное** задание и Enter.
Пример: проанализировать структуру выбранного проекта и предложить улучшения.
Ввод не отображается. При невозможности скрытого ввода команда отказывается
читать текст открыто. Пустой ввод и более 32768 символов отклоняются до запуска.
Параметра с текстом задания в командной строке нет.

`--cwd` — существующая папка для анализа. Профиль фиксирован: `exec --json
--sandbox read-only --ephemeral --ignore-user-config --skip-git-repo-check -`.
Текст передаётся в stdin через pipe. Этот способ подтверждён справкой локального
CLI 0.167.0 и [официальной документацией OpenAI](https://learn.chatgpt.com/docs/developer-commands?surface=cli).
Дополнительных прав записи, bypass sandbox или изменения глобальной конфигурации нет.
Read-only ограничивает запись, но не является гарантией чтения исключительно cwd.
Выбирайте папку и задание с учётом обычных прав установленного Codex.

На Windows к команде добавляется `-c` со значением аргумента
`windows.sandbox="elevated"`, передаваемым без shell. Это явно выбирает
нативную реализацию sandbox: `--ignore-user-config` иначе исключает также
пользовательскую настройку `windows.sandbox`, и CLI 0.167.0 может отклонять даже
`Get-Content` с `blocked by policy`. Профиль доступа остаётся `read-only`.
Используется уже настроенный elevated sandbox; обёртка не выполняет его установку,
не меняет глобальный config, ACL или firewall и не переключается на полный доступ.
Если sandbox не подготовлен или действует управляемый запрет, требуется отдельно
разобрать настройку Codex, а не отключать ограничения. См.
[официальную документацию OpenAI о Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox).

Проверено реальным CLI 0.167.0 на временном файле с публичным тестовым содержимым:
без выбора Windows sandbox чтение блокируется до запуска команды; с явным
`elevated` команда `Get-Content` возвращает содержимое, код выхода 0.
`verified`/`DONE` подтверждает завершение ответа даже тогда, когда в ответе Codex
сообщает об отказе инструмента. Это не автоматическая оценка выполнения задания.

`--timeout-seconds` по умолчанию 1800, допустимо 10–7200. Унаследованы лимиты
stdout/stderr 1 МиБ и строки JSONL 262144 символа. Вывод команды чтения файлов
может находиться целиком в одном JSON-событии, поэтому прежний предел 65536
символов прерывал обычный анализ больших документов. Превышение длины теперь
даёт `output_limit` с `parser_reason=line_limit`, без сохранения содержимого.
Проверки покрывают события с 90000 ASCII/UTF-8 символов, отказ при превышении
лимита строки и общий предел потока. Дополнительно реальный CLI 0.167.0 прочитал
публичный временный файл около 84 КБ через `Get-Content -Raw`, вернул обе контрольные
метки и завершился с verified/DONE. Для больших проектов читайте документы частями:
предел потока действует на весь запуск, а не на каждый файл отдельно.
Превышение/повреждение потока
останавливает проверку с неподтверждённым исходом. Возобновление существующего
хода и восстановление парсера после аварии не добавлены.

Без `--show-answer` выводится только JSON-отчёт. С этим флагом последний полученный
agent_message показывается между разделителями после подтверждённого DONE;
терминальные управляющие символы удаляются. Показ ограничен 32768 символами с
явной отметкой усечения. Не завершённый/ошибочный ответ не показывается как результат.
Ответ существует в памяти клиента до показа; программа не записывает его в файлы
или очередь. Перенаправление stdout самим пользователем, конечно, сохраняет вывод.

## Статусы

START сразу создаёт серверный last_reported_state=WORKING. Промежуточные item
не создают отдельные WORKING: наличие heartbeat отражает доступность клиента.

| Наблюдение | Отчёт/событие |
|---|---|
| turn.completed и выход 0 | verified, DONE; корректность ответа не гарантируется |
| turn.failed с поддерживаемой структурой и ненулевой выход | failed, ERROR |
| Ctrl+C при активном, корректно начатом ходе без конечного события | cancelled; после остановки дочернего процесса — INTERRUPTED |
| Неизвестный/повреждённый поток, EOF без конечного события, аварийный выход, тайм-аут | UNKNOWN, без вымышленного DONE/ERROR/INTERRUPTED |
| Отмена до START | Без конечного события |

Ошибки `error` общего уровня остаются консервативным UNKNOWN: они не доказывают
исход конкретного хода. Конфликтующие признаки завершения также не считаются успехом.
При Ctrl+C прекращается только созданный процесс/его доступное дерево; другие
сессии Codex не ищутся и не останавливаются. Ограничения очистки дерева процессов
из [smoke-проверки](exec-smoke.md) сохраняются. При cleanup_failed результат не verified.

После выхода выполняется ограниченная отправка очереди. Отчёт содержит отдельно
исход задания (`exec`) и связь/ожидающие события (`connected`, `pending`, `blocked`).
Верхние exec_failed/exec_interrupted/exec_not_verified не означают потерю очереди.
При недоступном API допустим verified в exec и pending > 0: задача завершена,
доставка ещё нет. После восстановления использовать прежнюю команду `flush`.
Повторное Ctrl+C во время отправки может отложить её; уже записанные события сохраняются.

## Приватность и параллельные команды

Текст задания не помещается в argv дочернего Codex, JSON-отчёт, backend или outbox.
В телеметрии только прежние пять полей события. Программа не создаёт prompt/output
файлов и запрашивает ephemeral для CLI; это не обещание отключить диагностику
самого CLI или хранение данных провайдером. Задание и выбранный контекст по обычной
схеме передаются модели Codex. Восстановление очереди не требует хранения задания.

run-task, run-smoke и flush используют взаимное исключение на одну outbox.
Второй процесс получает already_running **до ввода задания/запуска модели**.
Файл `*.monitor.lock` не содержит PID, ключей и текста; исключён из Git.
Дескриптор освобождается при выходе/аварии процесса, сам файл не удаляется.
status остаётся локальным чтением. Очередь и её квоты/привязки не менялись.

Проверки ERROR/Ctrl+C/тайм-аута/аварии используют контролируемые Python-процессы
и тестовый API, без дополнительных запросов к модели. Дополнительно выполнен один
реальный успешный stdin-запуск CLI 0.167.0 с DPAPI, собственной временной outbox
и настоящим локальным HTTP backend: delivered, connected=true, pending=0,
серверные события ровно START/DONE. Это не реальная проверка всех вариантов
ошибок/прерываний самого Codex CLI и не приёмка на Debian/SmallTV.
