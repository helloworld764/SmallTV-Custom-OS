# Storm OS — контролируемая проверка реального Codex CLI

Владелец сообщил результат диагностики: Codex CLI **0.167.0**, базовые флаги
JSON/sandbox/read-only распознаны, real_run_checked=false. Это проверка справки,
а не фактических событий. Из среды агента CLI по-прежнему не найден, поэтому
реальный тест здесь не выполнен и аппаратная/сетевая совместимость не объявляется.

## Запуск в обычном PowerShell

Из корня проекта:

```powershell
.\.venv\Scripts\python.exe codex-monitor/smoke_exec.py --run
```

Это уже **одна настоящая задача Codex** с коротким фиксированным запросом ответить
STORM_OK без инструментов и чтения файлов. Используются обычная авторизация и
лимиты установленного CLI; новых ключей, подписок и библиотек не требуется.
Без --run задача не запускается: выводится requires_run_flag и код выхода 1.

Перед запуском утилита проверяет --version/справку и дополнительные флаги.
Если нужных флагов нет, выводит unsupported_smoke_profile без попытки exec.
Никакого автоматического расширения прав или небезопасного запасного режима.
Профиль использует --ignore-user-config, --ephemeral, --sandbox read-only,
--skip-git-repo-check и --json. Назначение этих флагов описано в
[официальной документации OpenAI](https://learn.chatgpt.com/docs/non-interactive-mode).
Обход sandbox/правил не включается, hooks не устанавливаются.

Рабочая папка — новая пустая storm-exec-smoke-* в системном temp **вне проекта**,
чтобы не наследовать Git-контекст и AGENTS.md репозитория. Существующие сеансы
Codex не подключаются и не останавливаются. Утилита не читает и не меняет
auth/config пользователя; сам установленный CLI может читать служебные файлы
для своей работы. --ephemeral запрашивает отключение сохранения rollout этой
сессии; это не обещание отключить всю диагностику самого CLI.

Лимит ожидания — 120 секунд. stdout разбирается в памяти, stderr читается отдельно
и отбрасывается. Лимит каждого потока — 1 МиБ; очередь ограничена, длина строки
проверяется до передачи парсеру. Сырые потоки на диск и в вывод не попадают.
Новая временная папка удаляется только после проверки её точного пути и префикса.
Рабочая БД, backend, UI и Debian не участвуют.

## Отчёт

JSON содержит версию, статус, факт попытки реального запуска, численный код выхода,
счётчики только заранее известных типов, число неизвестных событий, результат
парсера/фиксированный reason и булевы признаки ответа STORM_OK и наличия stderr.
Никаких имён задач, thread/run IDs, путей, команд или содержимого ответов/ошибок.

- verified: этот один поток принят парсером, получен ожидаемый ответ и согласованный
  выход 0. Это не проверка остальных сценариев Codex, hooks или постоянного Monitor.
- unexpected_result/parser_rejected: условия не подтверждены; не считать успехом.
- timeout/output_limit/cancelled: тест остановлен, подтверждения совместимости нет.
- not_found/probe_failed/unsupported_smoke_profile: реальные события не проверены.
- cleanup_failed: завершение/закрытие потоков не подтверждено; не считать успехом.
  В этом случае следует проверить оставшийся именно тестовый процесс вручную.

На Windows завершение по тайм-ауту сначала адресуется дереву только созданного
процесса через taskkill. Если taskkill не завершил прямой дочерний процесс,
применяется process.kill к нему. Унаследованные незакрывшиеся pipes приводят к
cleanup_failed. Это не гарантия завершения произвольных отсоединившихся потомков;
штатный тест не просит запускать инструменты. Чужие процессы по имени не ищутся.

При verified код утилиты 0, при остальных статусах — 1. Можно прислать сюда этот
JSON-отчёт; сырой JSONL, auth-файлы и stderr пересылать не нужно. Никаких событий
Storm/heartbeat на сервер не отправляется. Даже успешный тест не означает, что
реализованы постоянная обёртка, очередь доставки или хранение agent-ключа.

Автотесты используют локальные Python-процессы с синтетическим выводом, без модели.
Они проверяют парсер, stdout/stderr, тайм-аут, лимиты и очистку новой папки. Настоящий
Codex остаётся отдельной ручной проверкой владельца из-за границ доступа среды агента.
