# Storm OS — идентичности будущих Windows Codex Monitor

Реализована только серверная авторизация программного агента. Агент на Windows,
hooks/events Codex CLI, WORKING/DONE/ERROR и установка службы пока
не реализованы. Регистрация не доказывает наличие Codex, запуск процесса или
доступность Windows. `kind=codex_windows` обозначает назначение протокола,
а не проверенную операционную систему клиента.

## API

| Метод / маршрут | Доступ | Результат |
|---|---|---|
| POST `/api/v1/agents/codex` | Сессия + CSRF | `{name}` → `agent_id`, одноразово показанный `token`; 201 |
| GET `/api/v1/agents/codex` | Сессия | Свои регистрации; super_admin видит все. limit 1–100, offset |
| GET `/api/v1/agents/codex/{id}` | Владелец или super_admin | Метаданные без credentials |
| GET `/api/v1/agents/codex/identity` | Bearer-ключ агента | Только `agent_id`, `kind` текущего агента |
| POST `/api/v1/agents/codex/heartbeat` | Bearer-ключ агента | Тело `{}`, серверная отметка связи; 204 |
| GET `/api/v1/agents/codex/{id}/presence` | Владелец или super_admin | Состояние связи и время последнего принятого heartbeat |
| POST `/api/v1/agents/codex/{id}/credentials/rotate` | Владелец или super_admin + CSRF | Новый ключ, старый сразу недействителен |
| POST `/api/v1/agents/codex/{id}/credentials/revoke` | Те же права + CSRF | Отзыв ключа; 204, повторный отзыв безопасен |

Имя — 1–80 символов после удаления пробелов по краям. owner_id/role нельзя
передать в теле создания. Регистрация всегда принадлежит текущему пользователю.
Лимит — 20 регистраций на владельца, включая регистрации с отозванным ключом;
для повторного подключения следует переиспользовать регистрацию через rotate.
Удаление зарегистрированных сущностей на этом этапе не добавлено.

Ключ содержит 32 случайных байта и технический префикс `smalltv_agent_`.
В SQLite только SHA-256. Исходное значение нельзя прочитать повторно. Не храните
его в Git/URL/чатах/логах; передача реальному Windows-агенту будет отдельным этапом.
За пределами доверенной локальной среды по ТЗ нужен защищённый транспорт.
Новый публичный доступ, CORS или TLS gateway этот этап не настраивает.

## Разделение полномочий

- Ключ агента разрешает запрос своей identity и отправку своего heartbeat. Он не даёт права
  читать списки пользователей/агентов/устройств, чужие метаданные или менять настройки.
- Cookie пользователя и ключ устройства не подходят для identity агента.
- Ключ агента не подходит для device state или пользовательской сессии.
- Чужой и отсутствующий ресурс одинаково дают 404 при доступе пользователя.
- Отключение аккаунта владельца блокирует его ключи; текущая роль администратора
  перечитывается из БД при каждом пользовательском запросе.
- Аудит содержит тип действия, actor_id и agent_id; исходные ключи не записываются.
- Отзыв/замена ключа выполняются в транзакции; пользовательские данные не удаляются.

Миграция 0004 добавляет `codex_agents` и `agent_credentials`, не изменяя миграции
0001–0003. При restore-db ключи агентов в восстановленной копии отзываются вместе
с пользовательскими сессиями, ключами устройств и кодами привязки. Метаданные
регистраций сохраняются; оригинал и файл backup не меняются.

## Границы следующего этапа

Веб-панель не расширялась; для ручного исследования API доступен существующий
OpenAPI `/docs`. Перед добавлением управления агентами в Storm Control Panel
нужно согласовать функции панели. Следующим отдельным этапом можно добавить
события с run_id/идемпотентностью. Источник реальных
событий Codex CLI сначала нужно проверить на установленной Windows-версии.
Потеря связи не должна превращаться в DONE или ERROR задания.

## Heartbeat и свежесть связи

Серверный протокол реализован без фонового агента. POST heartbeat требует JSON `{}`:
agent_id берётся из ключа, время — только с сервера. Поля state/run_id/timestamp
и любые другие поля отклоняются (422); отсутствие Bearer, cookie вместо ключа,
device-ключ, отозванный ключ или неактивный владелец дают 401. CSRF не нужен
для Bearer-запроса. Это сообщение не сообщает статус задания и не доказывает,
что Windows, Codex или физический компьютер исправны.

GET presence возвращает `agent_id`, `state`, `last_seen_at` (Unix seconds или null),
`server_time`, `stale_after_seconds`, `offline_after_seconds`; ответ не кэшируется.
Каждый агент имеет собственную отметку. Рекомендуемый интервал будущего клиента —
10 секунд, timeout и backoff при сбоях. Не отправлять накопленную очередь heartbeat
после восстановления: нужно отправить одну новую отметку текущей доступности.

| Условие | state |
|---|---|
| Отметки ещё нет | UNKNOWN |
| Возраст меньше stale-порога | ONLINE |
| Возраст от stale до offline, не включая offline | STALE |
| Возраст равен offline-порогу или больше | OFFLINE |
| Ключ отозван или аккаунт владельца отключён | OFFLINE |
| Сохранённая отметка позже текущего серверного времени | UNKNOWN |

`SMALLTV_AGENT_STALE_SECONDS` по умолчанию 30 (10–3600),
`SMALLTV_AGENT_OFFLINE_SECONDS` — 90 (15–86400), строго больше stale.
На границах порогов состояние уже STALE/OFFLINE. Состояние вычисляется при чтении,
без фонового таймера и отдельного процесса. ONLINE означает свежий принятый запрос,
а не гарантию непрерывной связи: потеря сети обнаруживается с задержкой до тайм-аута.
Состояния задания DONE/ERROR/WORKING здесь отсутствуют и не выводятся из тайм-аута.

Принятые heartbeat записываются не чаще одного раза в 5 секунд на агента.
Более частый запрос даёт 429 с `Retry-After`, не освежая отметку. Проверка и запись
транзакционные; ключ повторно проверяется под write-lock после аутентификации,
чтобы конкурирующий отзыв/замена не позволили старому ключу освежить связь.
Не создаётся строка аудита на каждый heartbeat и не хранится неограниченная история.
Ограничение защищает частоту записей, но не заменяет будущую защиту публичного gateway.

Миграция 0005 добавляет `agent_presence`: одна строка на агента. После рестарта
backend прежняя отметка сохраняется и оценивается по текущему возрасту. При переводе
часов назад используется UNKNOWN до нового heartbeat; доверять времени клиента нельзя.
Ротация/отзыв ключа очищают отметку: новый ключ должен отправить новый heartbeat.
Restore-db очищает отметки и отзывает ключи только в новой копии, не меняя источник.
Device heartbeat, события Codex, UI статуса и сам Windows Monitor остаются будущими этапами.
