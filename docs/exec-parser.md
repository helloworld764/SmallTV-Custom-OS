# Storm OS — автономный парсер JSONL Codex

`codex-monitor/exec_events.py` — библиотека стандартного Python без новых
зависимостей. Это тестируемая основа будущей обёртки, а не работающий Windows
Monitor. Она не запускает процессы, не читает файлы/настройки Codex, не сохраняет
очередь и не отправляет heartbeat или HTTP-запросы. Backend и UI не изменены.

Общая форма JSONL и имена типов сверены с
[официальной документацией OpenAI](https://learn.chatgpt.com/docs/non-interactive-mode).
Поддерживаемая ниже комбинация полей — консервативный профиль прототипа, проверенный
на синтетических данных и одном штатном запуске CLI 0.167.0 у владельца.
Остальные реальные сценарии ещё не подтверждены:
[исследование и диагностика](codex-cli-research.md).

## Контракт библиотеки

Создать `ExecEvents()` для одного явно отслеживаемого процесса и одного хода.
Передавать в `feed(line)` отдельные уже собранные строки stdout. Байтовые фрагменты,
stderr и обычный текстовый вывод не являются подходящим входом. Будущая обёртка
должна ограничивать буфер ещё до сборки строки; этот парсер проверяет её готовый
размер (до 1048576 символов), но не является stream-reader. Превышение даёт
`line_limit`; неверный тип входа — `invalid_line`. Общий байтовый предел stdout
в обёртке остаётся 1 МиБ.

`feed()` возвращает список из нуля/одного неизменяемого `StormEvent`.
`to_dict()` содержит только event_id, run_id, sequence, kind, occurred_at — поля
[серверного контракта](codex-events.md). Run/event UUID создаёт библиотека,
время берётся с локальных часов, а не из входных сообщений. Исходные объекты
JSON не хранятся в состоянии парсера. Тексты item/error, команды, пути,
thread_id и usage не включаются в выходные события.

| Вход/наблюдение | Результат прототипа |
|---|---|
| Необязательный thread.started до начала хода | Проверить непустой thread_id, не сохранять его |
| Первый turn.started | START с sequence=1 |
| item.started/updated/completed во время хода | Проверить оболочку item.id/type, не копировать содержимое |
| turn.completed с целыми неотрицательными input_tokens/cached_input_tokens/output_tokens в usage | Запомнить кандидата DONE, пока ничего не отправлять |
| turn.failed с error.message строкой | Запомнить кандидата ERROR без текста |
| error, неизвестный тип, неверный порядок/структура | Запретить конечный отчёт, локальный UNKNOWN |
| EOF/код выхода без подтверждающего конечного события | UNKNOWN, без вымышленного DONE/ERROR |

После окончания процесса вызвать `finish(exit_code)`. Кандидат DONE требует
кода 0; кандидат ERROR — наблюдаемого ненулевого кода. None означает, что код
неизвестен. Противоречия оставляют UNKNOWN. Только тогда выдаётся одно конечное
событие с sequence=2. Промежуточные WORKING здесь не генерируются: сервер уже
трактует START как WORKING, а политика частоты прогресса будет задачей обёртки.

`finish(..., cancelled_by_user=True)` выдаёт INTERRUPTED только для начатого,
неповреждённого хода без конечного события. Это доверенное наблюдение вызывающего
кода о явной отмене пользователем, а не вывод из пропажи сети/процесса. Команда
run-task вызывает его после Ctrl+C и остановки своего дочернего процесса. Противоречие с
конечным событием остаётся UNKNOWN. Без START конечных сообщений не бывает.

`outcome` остаётся UNKNOWN до согласованного `finish`; `reason` содержит только
фиксированный диагностический код, без входного текста. Повторный finish не
повторяет события. После finish вызов feed запрещён (RuntimeError).
Повторные START, несколько ходов в одном процессе и повторные конечные события
считаются неподдерживаемым порядком; для их поддержки нужен отдельный дизайн.

Повреждённый JSON, дубли JSON-ключей, NaN/Infinity, слишком большая/глубокая строка
и неверная отметка локальных часов блокируют последующий успех этого экземпляра.
Пустые строки игнорируются. Профиль сознательно может дать UNKNOWN для валидной,
но пока неподдерживаемой версии CLI. Ошибка отдельного инструмента, завершённый
item или текст ответа не доказывают завершение всего хода.

## Границы проверки

Синтетические тесты покрывают конечные состояния, согласование с exit code,
неполные/повреждённые потоки, порядок, приватность выходных полей и разделение run.
Дополнительный тест передаёт отчёты через FastAPI TestClient в изолированную SQLite:
START/DONE принимаются, повтор подтверждается без второй записи, presence остаётся
UNKNOWN без heartbeat. Это проверка программных контрактов, не реальный запуск Codex.

До реальной эксплуатации нужны: проверка установленной версии и контролируемого
потока, чтение stdout без блокировки, управление собственным процессом, надёжная
отправка/очередь с сохранением event_id, хранение ключа и независимый heartbeat.
Истечение тайм-аута будущей обёртки не должно превращаться в DONE; состояние связи и исторический
last_reported_state backend по-прежнему различаются. Восстановление состояния
самого парсера после его аварии и повторный разбор файла этим этапом не добавлены.
Сырые журналы пользователя для тестов не нужны; их нельзя коммитить или пересылать.

Локальная обёртка, отправка и очередь реализованы для явно запускаемых read-only
задач: [task-runner.md](task-runner.md). Успешный реальный stdin-запуск CLI 0.167.0
проверен вместе с DPAPI и локальным HTTP backend. Постоянное наблюдение за всеми
сессиями и удалённый транспорт не добавлены.
