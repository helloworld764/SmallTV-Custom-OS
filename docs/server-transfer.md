# Перенос, запуск и восстановление Storm OS

Это подготовленная инструкция и шаблоны. Развёртывание, службы, SSH, firewall
и питание Debian агентом не настраивались. Codex CLI и Monitor остаются Windows.

## Проверяемая поставка

Исходные диапазоны requirements.txt сохранены; для установки проверенной версии
используйте requirements-runtime.lock или requirements-dev.lock. Проверяемые
платформы этого этапа: Windows Python3.12 и Linux/WSL Python3.13, Node24 для JS.
Python/venv/pip должны уже быть установлены. `.venv` не копируется между ОС.

```powershell
.\.venv\Scripts\python.exe tools/build_release.py --output dist/storm-source.zip
.\.venv\Scripts\python.exe tools/verify_release.py dist/storm-source.zip
```

Имена должны быть новыми: существующий zip не перезаписывается. Manifest
перечисляет SHA256 всех файлов; повторная сборка неизменённых исходников
даёт побайтно одинаковый zip. Это контроль целостности, не цифровая подпись:
получайте пакет из доверенного источника и сверяйте переданный SHA256 отдельно.
Пакет включает backend/миграции, web, публичные ресурсы, fonts/лицензию,
инструменты, документацию, шаблоны. Нет `.env`, DPAPI, SQLite/WAL, пользовательских
обоев/изображений, виртуальных окружений, кэшей, архива приватных рисунков Null.
`--include-tests` добавляет тесты; проверки исходного архива рисунков требуют
отдельных dev-fixtures, в серверный пакет они не входят.

Проверка zip отвергает traversal, абсолютные пути, symlinks, дубли, повреждения
и несоответствие manifest. Распаковывать только в новый пустой каталог.
Не накладывать новый пакет поверх старой рабочей версии и не удалять старую.

## Размещение при последующем согласованном развёртывании

Предлагается: `/opt/storm/releases/<version>` — код и собственная .venv версии,
`/opt/storm/current` — выбранная версия, `/var/lib/storm` — постоянная SQLite,
`/etc/storm/storm.env` — конфигурация вне Git, закрытые backups — отдельно.
Пользователь `storm` непривилегированный, запись только в каталог данных.
Создание пользователя/каталогов/прав и переключение current выполняются отдельно.

В новой версии, до переключения рабочей службы:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements-runtime.lock
```

Для разработки/проверки вместо runtime используйте requirements-dev.lock,
затем `.venv/bin/python -m pytest -q` и `node --test tests/*.test.mjs`.
Не направлять тестовый запуск на рабочую БД; обычные тесты создают свои tmp-БД.
Локальная проверка серверного пакета использует Settings(_env_file=None) и
синтетические аккаунты. Не включать настоящего Telegram worker в тестах.

Перед переносом остановить Windows bot worker: один token — один polling
worker, даже если работают два разных компьютера. Для окончательной копии
также остановить backend/Monitor, чтобы после backup не потерять новые изменения.
Создать/проверить backup описанными командами [backups.md](backups.md), перенести
его отдельно защищённым каналом. `.env` и ключи никогда не включать в Git/zip.

На сервере проверить копию и восстановить её в НОВЫЙ файл:

```bash
.venv/bin/python -m backend.app.manage verify-backup --source /private/snapshot.sqlite3
.venv/bin/python -m backend.app.manage restore-db --source /private/snapshot.sqlite3 --output /var/lib/storm/restored.sqlite3
```

Путь SMALLTV_DB_PATH при restore не должен совпадать с источником/выходом.
Только после успешной проверки выбрать restored.sqlite3 в конфигурации.
Данные питомцев, настройки, пользователи и изображения сохраняются. Восстановление
отзывает сессии, device/agent keys и коды, очищает heartbeat, Telegram-привязки,
очередь ответов и отложенные напоминания сна: требуются новый вход, повторная
привязка бота и выдача ключей. Старый DPAPI Monitor не подходит. Повторное
подключение — обязательная проверка, а не потеря игровых данных.

Новый token бота остаётся в закрытом EnvironmentFile. Для ручного запуска
можно экспортировать SMALLTV_* в окружение, затем из корня версии:

```bash
.venv/bin/python -m backend.app
# В отдельном процессе, только после проверки и остановки старого worker:
.venv/bin/python -m backend.app.bot_worker run
```

Backend слушает127.0.0.1, HTTPS завершается на отдельно согласованном reverse
proxy. `COOKIE_SECURE=true` требует HTTPS в браузере; для изолированного
локального HTTP-теста используется false. Не выставлять `0.0.0.0`/публичный
порт ради обхода настройки TLS. Не отключать проверку сертификата Monitor.

Шаблоны `deploy/*.service.example` содержат одного backend и одного bot worker,
WorkingDirectory, отдельного пользователя, EnvironmentFile, рестарт и ограничения
записи. Они НЕ установлены и не проверены на целевом Debian. Перед установкой
проверить реальные пути, права, CA, доступ к DNS/Telegram, поддержку sandbox
systemd; старт/enable и любые изменения ОС требуют отдельного задания.

## Приёмка и обновление

1. `/health`200 означает только liveness. Также проверить вход, список своих
   устройств, чтение/сохранение настроек, simulator?device=…, свой питомец.
2. Новым device key проверить display/events/asset,401 старым и404 чужому.
3. Привязать Telegram, проверить кнопки/уход/часовой сон и разрешения уведомлений.
4. Из Windows переключить Monitor на HTTPS по [monitor-server.md](monitor-server.md);
   проверить heartbeat/доставку/обрыв без ложного DONE.
5. Перед обновлением новая проверенная версия, backup и пробный restore в новый
   файл; миграции сначала проверять на копии. Не запускать одновременно старую
   и новую версии на одной БД. Обновление меняет код и схему только после остановки.
6. При сбое сохранить новую БД/логи, остановить процессы. Если схема изменилась,
   откатить код вместе с проверенной новой восстановленной копией старого backup,
   а не запускать старый код на неизвестной схеме. Старые файлы не перетирать.

После переноса обязателен реальный длительный72-часовой тест: сеть/перезапуск,
память/диск, SQLite busy, Telegram retry, Monitor outbox, backup/restore.
Короткие автоматические fault-тесты не заменяют72часа и проверку отключения
питания. SmallTV добавляется в приёмку только после определения платы и recovery.

## Изолированная Linux-проверка без развёртывания

`tools/validate_linux.py` принимает bundle с тестами, локальный Linux-wheelhouse,
проверенный по официальному Node SHASUMS256.txt Linux tar.xz; создаёт только
`/tmp/storm-validation-*`, venv без системных установок. Выполняет Python/JS и
native C++-тест. `--art-fixtures` может указать локальный assets/pets для всех
проверок исходных одобренных рисунков; они остаются в локальном временном каталоге.
Это тест переносимости Linux, не развёртывание на Debian.

Браузерные тесты Windows используют отдельный профиль Chrome и локальный CDP:
ожидают реальный отчёт проверок, сохраняют screenshot и закрывают свой браузер.
Проверки геометрии/перекрытий не отключены. Нужен Node24 с WebSocket;
без Chrome Linux помечает только эти восемь проверок skipped.
