# Storm OS — серверные события Codex

Это собственный протокол Storm OS для локального Windows Monitor. Он не является
проверенным API Codex CLI. Постоянный Monitor всех сессий, экран Codex,
общая очередь доставки на устройство ещё не реализованы. Для браузерного превью
есть узкая проекция конечных событий с TTL и оверлеями:
[simulator-notifications.md](simulator-notifications.md).
Добавлен ограниченный локальный мост run-smoke/run-task с очередью/heartbeat:
[local-monitor.md](local-monitor.md). Постоянный Monitor произвольных задач
не реализован. Автотесты используют программные события в изолированном backend.

## Контракт

| Метод / путь | Авторизация | Результат |
|---|---|---|
| POST `/api/v1/agents/codex/events` | Отдельный Bearer-ключ агента | 201 — новое событие; 200 — точный повтор |
| GET `/api/v1/agents/codex/{agent_id}/runs` | Сессия владельца или super_admin | Список заданий, limit 1–100 (50), offset ≥ 0 |
| GET `/api/v1/agents/codex/{agent_id}/runs/{run_id}` | Те же права | Последнее сообщённое состояние задания |
| GET `/api/v1/agents/codex/{agent_id}/runs/{run_id}/events` | Те же права | События по sequence, after_sequence ≥ 0 (0), limit 1–100 (50) |

POST принимает только эти поля:

```json
{
  "event_id": "11111111-1111-4111-8111-111111111111",
  "run_id": "22222222-2222-4222-8222-222222222222",
  "sequence": 1,
  "kind": "START",
  "occurred_at": 1794000000
}
```

UUID здесь фиктивные; клиент создаёт новые UUID для каждого задания и события.
Agent ID определяется ключом, его нельзя указать в теле. sequence — целое число
1–10000; occurred_at — целые Unix seconds 0–253402300799 (заявленное время клиента).
Булевы значения и строки вместо чисел отклоняются. Прочие поля дают 422.
Промпты, ответы, имена файлов, командные строки, произвольные логи и секреты не
включены в протокол. Заголовок задания/описание ошибки потребуют отдельного дизайна
приватности. Валидация не возвращает исходное тело ошибочного запроса.

Ответ POST: `event_id`, `run_id`, `sequence`, `duplicate` (boolean). Состояние задания
читается отдельным GET. Все ответы API имеют Cache-Control: no-store.
Cookie пользователя или device-ключ не разрешают отправку событий. Agent-ключ
не даёт читать списки и историю. POST не требует CSRF, потому что использует Bearer.
Чужой агент или отсутствующий ресурс при пользовательском чтении дают 404;
отсутствующая/неподходящая авторизация — 401. TLS вне доверенной локальной среды
остаётся обязательным требованием будущего развёртывания.

## Переходы и повторы

- Первое событие — START с sequence=1. Оно создаёт run со state WORKING.
- Затем разрешены WORKING, DONE, ERROR или INTERRUPTED строго с предыдущим sequence + 1.
- DONE/ERROR/INTERRUPTED завершают именно это задание. Новые события после них
  запрещены; для следующего задания нужен новый run_id. Повторный START запрещён.
- event_id уникален в пределах агента. Точный повтор всех нормализованных полей
  возвращает 200 с duplicate=true, даже после завершения задания и рестарта backend.
  Запись, её received_at и состояние run при этом не меняются.
- Тот же event_id с иным содержимым, иной event_id с занятым sequence,
  пропуск/перестановка sequence или неверный переход дают 409 без изменений БД.
  После 409 клиент должен разобраться с очередью, а не автоматически создавать новый ID.
- При потере ответа клиент повторяет тот же event_id и неизменное тело.
  Порядок отправки — последовательный в рамках run. Несколько run могут выполняться
  параллельно; одинаковые UUID у разных агентов не смешивают данные.

Проверка ключа, повтора, порядка, лимитов, запись события и изменение run выполняются
в одной BEGIN IMMEDIATE транзакции. Ключ перепроверяется под write-lock, чтобы отзыв,
ротация или отключение владельца не позволяли запросу со старым доступом записать событие.
Конкурирующие точные повторы создают одну запись; из конфликтующих переходов принимается один.

## Время и связь

Run содержит agent_id, run_id, `last_reported_state`, last_sequence, started_at,
updated_at. Последние два поля — серверные Unix seconds при первом/последнем
принятом новом событии. Event содержит event_id, run_id, sequence, kind, occurred_at
и received_at. Время клиента носит информационный характер: оно может быть неточным
или идти назад и не используется для порядка, прав, rate limit или heartbeat.
Из этих времён пока не вычисляется подтверждённая длительность работы Codex.

`last_reported_state` — сохранённый отчёт, а не живой статус агента. Доступность
нужно читать отдельно через [presence](agent-identities.md#heartbeat-и-свежесть-связи).
События не освежают heartbeat: после сетевого сбоя может прийти очередь старых событий.
Без heartbeat состояние связи остаётся UNKNOWN, даже после принятия START/DONE.
OFFLINE/STALE не переписывают последнее состояние задания и не создают DONE,
ERROR или INTERRUPTED. Отсутствие заданий также не доказывает IDLE.
DONE означает полученное сообщение о завершении, а не проверенную правильность результата.

Список run сортируется по серверному updated_at убывающе, затем run_id. Это список
истории, а не выбор «активной задачи». Политика выбора при нескольких run, истечение
уведомлений и поведение экрана будут отдельным этапом; сейчас история не отправляется
на SmallTV и не воспроизводится как новое уведомление после восстановления копии.

## Лимиты и хранение

На агента принимается не более 120 новых событий за последние 60 секунд:
429 с Retry-After: 60. Точные повторы подтверждаются и при исчерпанном лимите;
отклонённые сообщения ничего не записывают. Лимит переживает рестарт, так как
опирается на серверные received_at в SQLite. Перевод серверных часов назад может
временно продлить ограничение; источник времени должен быть исправен.

Прототип ограничивает хранение на агента: 1000 run и 10000 событий суммарно.
При исчерпании квоты новые записи дают 429 без Retry-After: ожидание само не
освобождает место. Даже конечное событие может не поместиться; сервер сохраняет
последнее подтверждённое состояние и не подделывает результат. Точные повторы
по-прежнему подтверждаются. Новых run при лимите run не будет, но уже существующий
можно завершить, пока остаётся квота событий. Автоматического удаления истории нет:
политика архивации/хранения и операторский интерфейс будут отдельной задачей до
длительной эксплуатации. Квоты не заменяют ограничения сетевого gateway.

Миграция 0006 добавляет codex_runs/codex_events и индексы, не меняя старые миграции.
Рестарт, ротация ключа и restore-db сохраняют историю и защиту от повторов.
Restore-db отзывает credentials/сессии и очищает presence только в новой копии;
старый ключ не сможет продолжать запись. Рабочая БД и backup не изменяются.
