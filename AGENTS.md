# AGENTS.md — правила работы Codex в SmallTV Custom OS

> Этот файл предназначен для Codex CLI и других кодовых агентов. Язык общения и отчётов — русский. Имена программных сущностей, код и команды могут быть на английском.

## 1. Источник требований и приоритеты

1. **Перед любыми изменениями прочитай `TZ.md` полностью**, затем этот `AGENTS.md`, `README.md` (если есть) и документацию затрагиваемого компонента.
2. `TZ.md` — согласованное техническое задание; этот файл — порядок работы. Прямое указание владельца в текущей задаче определяет её границы, но при конфликте с ТЗ сначала запроси согласование, а не молча меняй требования.
3. Различай подтверждённые факты, гипотезы и открытые вопросы. Не выдавай предположения об ESP8266, дисплее, Flash, GPIO, OTA или API Codex за проверенные данные.
4. **Не начинай реализовывать всё ТЗ сразу.** Выполняй только текущую явно поставленную задачу. Не расширяй scope без разрешения.
5. Не изменяй `TZ.md`, архитектуру, требования или приоритеты без согласования владельца. После согласования обновляй версию/историю ТЗ.

## 2. Аппаратная и системная архитектура

- **Основной ноутбук:** Windows; на нём установлен и запускается Codex CLI. Здесь же работает будущий Windows Codex Monitor, отправляющий статусы на сервер.
- **Старый ноутбук:** Debian 13 XFCE, ASUS VivoBook, Pentium Silver N5000, 4 ГБ RAM, SSD 120 ГБ; здесь запускается FastAPI/SQLite, Telegram-бот, мониторинг и веб-панель.
- **Устройство:** GEEKMAGIC SmallTV-Ultra, предположительно ESP8266 и дисплей 240×240. Реальная ревизия и способ безопасной прошивки **пока не проверены**.
- **Начальный масштаб:** один SmallTV и один Debian backend. Многопользовательские сущности проектируются сразу, но без преждевременного развёртывания VPS.
- **В будущем:** если подключаются друзья, backend переносится на VPS, Debian освобождается от серверной роли; если остаётся одно устройство, backend остаётся на Debian и позже изолируется от пентест-лаборатории.
- **Codex НЕ переносить на Debian**. Не смешивать два ноутбука в инструкциях, конфигурации или тестах.

## 3. Стратегия выполнения задачи

Перед изменениями:

1. Кратко сформулируй цель, затрагиваемые файлы, допущения и критерии готовности.
2. Изучи существующий код и интерфейсы. Не переписывай рабочие компоненты без необходимости.
3. Если решение зависит от неизвестной ревизии SmallTV, официальных событий Codex CLI или другого непроверенного свойства — явно обозначь блокер и предложи безопасный временный интерфейс/заглушку.
4. Для существенных или рискованных изменений сначала представь короткий план; не выполняй разрушительные действия без подтверждения.

Во время работы:

- Делай минимальные, логически законченные изменения. Соблюдай текущие соглашения репозитория.
- Добавляй тесты на новую бизнес-логику и исправленные дефекты; проверяй ошибки, тайм-ауты и офлайн-сценарии.
- Не внедряй тяжёлые зависимости без обоснования. Сохраняй низкую нагрузку на N5000/4 ГБ и ESP8266.
- Не создавай фиктивные «успешные» статусы при потере связи; используй OFFLINE/UNKNOWN/STALE по смыслу.
- Не подменяй обещанную функциональность имитацией без явной пометки.

После изменений:

1. Выполни применимые тесты, линтеры, сборку или статическую проверку. Если проверить невозможно — прямо укажи почему.
2. Отчитайся: что изменено, какие файлы, какие команды проверены, что прошло/не прошло, какие риски и следующий небольшой шаг.
3. Не заявляй, что прошивка проверена на устройстве, если тестировалась только сборка или браузерный симулятор.

## 4. Границы до доставки SmallTV

**Можно:** аудит исходного репозитория `https://github.com/iodn/geekmagic-tv-esp8266` и его лицензии, проектирование API, backend, SQLite/миграции, мониторинг Debian, тесты, Telegram-бот, Tamagotchi, веб-панель, Windows Codex Monitor, документация, симулятор 240×240.

**Нельзя считать завершённым без реального устройства:** совместимость GPIO и дисплея, поведение кнопки, расход RAM/Flash, OTA, безопасный recovery, фактическая производительность анимаций, работа с локальной Wi-Fi конфигурацией.

**Симулятор** — инструмент разработки интерфейсов и событий, а не полноценная браузерная Tamagotchi-игра (она отложена).

## 5. Инварианты проекта

- **Один общий Telegram-бот** с разделами управления SmallTV и Tamagotchi. Личные Tamagotchi-боты пользователей — будущая функция.
- **Null — личный питомец владельца**, не общий. Общие питомцы: Pixel, Byte, Glitch.
- Пользователь может получить в Telegram стандартный промпт для генерации собственного питомца и загрузить изображение; сервер валидирует и конвертирует его под ограничения устройства.
- Постоянная точка состояния backend **на каждом экране**; при смене состояния краткое уведомление «Сервер включён»/«Сервер выключен». Потеря связи не доказывает физическое выключение ноутбука; предусмотреть debounce и предотвращение спама.
- События (Codex DONE/ERROR, серверные предупреждения) временно перекрывают экран с возвратом к предыдущему. Приоритеты и дедупликация обязательны.
- **Codex Monitor работает на Windows**; отслеживание обычных интерактивных сеансов зависит от проверенных событий/обёртки. Не обещать интеграцию с официальным приложением ChatGPT.
- Полные настройки устройства и администрирование — в веб-панели; Telegram — управление и базовые настройки. Super Admin имеет доступ ко всем устройствам; обычный пользователь — только к своим.
- Браузерная игра Tamagotchi, персональные Telegram-боты, масштабирование на друзей и VPS — **не включать в v1 без отдельного решения**.

## 6. Рекомендуемый стек и правила кода

- **Firmware:** C++/PlatformIO, только после проверки целевой платы и библиотек. Беречь heap/Flash, не использовать тяжёлую графику и динамические аллокации без оценки.
- **Backend:** Python + FastAPI, SQLite с миграциями, конфигурация из окружения, минимальное число процессов; `systemd` для эксплуатации Debian.
- **Windows monitor:** лёгкий агент/обёртка, с явными статусами `WORKING`, `DONE`, `ERROR`, `OFFLINE`/`UNKNOWN`, heartbeat и тайм-аутами.
- **Frontend:** лёгкая веб-панель без тяжёлой инфраструктуры по умолчанию.
- **API:** версионирование, схема данных, явные ошибки, тайм-ауты, контроль доступа на сервере; не зашивать IP/домены/токены в исходники.
- **Данные:** миграции SQLite, транзакции, резервные копии и тест восстановления; не удалять пользовательские данные автоматически.
- **Репозиторий:** придерживаться структуры из `TZ.md`, адаптировать только по согласованию; не создавать лишние сервисы или каталоги ради формальности.
- **Зависимости:** фиксировать версии или допустимые диапазоны, документировать установку, проверять лицензии сторонних исходников и ресурсов.

## 7. Безопасность и опасные операции

- Не коммитить `.env`, реальные токены Telegram, пароли, API-ключи, приватные ключи, пользовательские данные и резервные копии. Поддерживать `.env.example` с фиктивными значениями и `.gitignore`.
- Backend запускать от отдельного **непривилегированного пользователя**; не выдавать root без причины. Сложную изоляцию пентест-лаборатории пока не внедрять, но базовую защиту не отключать.
- Не открывать API, админ-панель или порты в публичный интернет без отдельного согласования, TLS, авторизации и анализа угроз. Для локальной сети использовать ограничение доступа.
- Любые запросы к чужим устройствам, питомцам и админ-функциям проверять по RBAC на backend, а не только скрывать кнопки в UI.
- Загрузки изображений ограничивать по размеру/типу/разрешению; декодировать безопасно и не доверять расширению файла.
- Перед командами, которые могут стереть данные, перепрошить устройство, менять разделы, firewall, SSH, сетевые настройки, права, `systemd` или питание ноутбука, **попросить явное подтверждение** и описать откат.
- Не выполнять `git reset --hard`, `git clean -fd`, принудительные push, удаление БД/бэкапов и массовые изменения без отдельного разрешения.
- OTA и физическую прошивку не проводить без проверенного метода восстановления. Не предполагать наличие dual-bank rollback.

## 8. Тестирование и критерии качества

- Проверять позитивные и негативные API-сценарии, ошибки авторизации, перезапуски, офлайн-режим, потерю heartbeat, дубли событий и восстановление SQLite.
- Проверять, что смена экрана не теряется после временного уведомления, а индикатор соединения есть на каждом экране.
- Для Tamagotchi проверять независимость питомцев разных пользователей и сохранность прогресса.
- Для Windows Codex Monitor проверять, что потеря Windows или сети **не порождает ложный `DONE`**.
- Симулятор 240×240 использовать для проверки UX, но не как доказательство пригодности ESP8266.
- Перед объявлением v1 готовой провести испытания на реальном устройстве, безопасную проверку OTA/recovery и целевой 72-часовой тест.

## 9. Первый рекомендуемый шаг

Если владелец просит начать разработку без более узкого задания, **не генерируй сразу весь проект**. Сначала изучи `TZ.md` и текущий репозиторий, проверь исходный проект и лицензию, затем предложи короткий план первого этапа. После подтверждения реализуй минимальный каркас и `GET /health` с тестами; дальнейшие модули — отдельными задачами.

## 10. Формат финального отчёта Codex

Пиши кратко по-русски: **результат → изменённые файлы → проверки (с командами и статусом) → риски/непроверенное → следующий шаг**. Не выдавай непроведённые проверки за выполненные. Если обнаружено противоречие с `TZ.md`, остановись и запроси решение владельца.
